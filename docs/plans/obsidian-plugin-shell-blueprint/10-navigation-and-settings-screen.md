# Task 10 · Navigation, view state, settings screen

Phase A. Needs: Task 09.

**Goal.** One registered view type; each open view has its own Vue app and its own typed route, which Obsidian saves in the workspace layout; the plugin tab is fixed and keeps its own history; the shell owns a settings screen whose sections the modules contribute through their screens manifest.

## Files

Create: `src/application/shell/{routes,history}.ts`, `src/application/routes.ts` (`SETTINGS_SECTIONS`, `SettingsSection`, `Route`, `appRoutes`, `RouteNameOf`, `SectionIdOf`), `src/presentation/shell/{routing,navigation,screens}.ts`, `src/presentation/shell/components/{AppFrame,RouteOutlet,SettingsScreen,NotFoundState}.vue`, `src/presentation/app-surface.ts`, `src/infrastructure/obsidian/shell/open-route.ts`; replace the bare view in `src/infrastructure/obsidian/shell/shell-view.ts`. The tracer's skeleton (Task 18 fills it): `src/application/items/{index,module,routes}.ts`, `src/application/items/i18n/{catalog,<language>}.ts`, `src/presentation/items/{index,screens}.ts`, `src/presentation/items/components/ItemSettings.vue`. Tests: `tests/unit/application/shell/{routes,history}.test.ts`, `tests/unit/application/routes.test.ts`, `tests/dom/presentation/shell/{navigation,settings-screen}.test.ts`, `tests/dom/infrastructure/shell/{shell-view,view-state,settings-state,open-route}.test.ts`, `tests/support/surface.ts`. Modify: `src/presentation/shell/{mount.ts,components/ShellApp.vue,host.ts,index.ts}`, `src/bootstrap.ts` (the view factory, `open` with `Route`), `src/application/commands.ts` (`Route` in `AppCommand`), `tests/support/preload.ts`, `tests/unit/application/modules.test.ts`.

## Steps

- [ ] **1. Routes are data** (`src/application/shell/routes.ts`): `RouteLike = { readonly name: string }`; `Routes<R> = { start, decode, equals }`; `routesOf(schema, start)` gives one, where `decode` never throws (an unknown name, a missing or broken parameter, or no object at all gives `start`) and `equals` compares by value (`Schema.toEquivalence`). `SETTINGS = "settings"`; `settingsRoute(sections)` = `Schema.Struct({ name: Schema.Literal(SETTINGS), section: Schema.Literals(sections) })`; `SettingsRoute`. No router library: a `switch` over route names, which typecheck checks, covers a handful of screens. No placeholder screens: a route exists only when its screen does.
- [ ] **2. The history** (`src/application/shell/history.ts`, plain data): `RouteHistory` with `historyAt`, `visit`, `stepBack`, `stepForward`; a visit pushes the current route onto the back stack and clears the forward stack; a visit to the current route pushes nothing; at most `HISTORY_LIMIT = 50` steps back. Test: `history.test.ts`.
- [ ] **3. Sections in the manifest.** Add `routes` and `sections: { id, order }[]` to `ModuleManifest`, and `sectionsOf` (ordered by `order`), `SectionOf`, `routeSchemasOf`, `RouteOf` to `src/application/module.ts`. `src/application/routes.ts`: `SETTINGS_SECTIONS = sectionsOf(APP_MODULES)`, `Route = Schema.Union([settingsRoute(SETTINGS_SECTIONS), ...routeSchemasOf(APP_MODULES)])`, `appRoutes = routesOf(Route, <start>)`, and `RouteNameOf<Name>`, `SectionIdOf<Name>` (the route names and section ids of one module). Put `Route` into `AppCommand` (Task 05) and into bootstrap's `open`. The settings route needs at least one section (`Schema.Literals` of an empty list does not type), so create the tracer module's skeleton now: `ITEMS_SECTION = "items"` in `src/application/items/routes.ts`, a manifest `defineModule({ name: "items", catalog, sections: [{ id: ITEMS_SECTION, order: 100 }] })` in `APP_MODULES` after `shell`, the start route `{ name: "settings", section: "items" }`, and a section component `ItemSettings.vue` (`data-testid="items-screen"`) that shows the tracer's empty state from its catalog, exported as `itemsSettings: Component` from `src/presentation/items/index.ts`; `src/presentation/items/screens.ts` is `{ screens: {}, sections: { items: { label, component: () => import("./index").then((m) => m.itemsSettings) } } } satisfies ModuleScreens<"items">` (step 4), and `MODULE_SCREENS` (step 5) holds `shell` and `items`. Task 18 replaces it with the real list; Task 17 adds the notes module's data issues with `order: 900`. Untested proposal: the tracer's manifest this early. If the skeleton makes a check fail that the real module would pass, give the shell a section `general` with one line of text from its catalog instead, and remove it in Task 18. Test: `tests/unit/application/routes.test.ts` pins `SETTINGS_SECTIONS` (a new section changes what the user sees, so this test changes with it).
- [ ] **4. Screens manifest** (`src/presentation/shell/routing.ts`, Vue-free, Vue only as types): `ScreenLoader = () => Promise<Component>`; `SettingsSectionPart = { label(catalog), component: ScreenLoader, badge?: ScreenLoader }`; `MenuEntry<R>` (`route`, `label(catalog)`, `icon` whose `lucide:*` name is in `SHELL_ICONS`); `ModuleScreens<Name>` = `{ screens, sections, menu?, context? }`, typed by the module's manifest (`RouteNameOf`, `SectionIdOf`) so a route without a screen, a section without a part or a part for an unknown id fails typecheck in the module; `SurfaceDefinition<R>` = `Routes<R>` plus `screen(route)` (`undefined` shows not-found), `menu`, `context?`, `sections?`; `frameMenu(definition)` adds the shell's settings entry (`catalog.shell.frame.settings`, `i-lucide-settings`) after the modules' entries whenever there is a section, opening the first section of `sections`; `ViewNavigation<R>` (`current()`, `history()`, `navigate(route)`, `back()`, `forward()`, `onChange(listener)` returning the unsubscribe) and `memoryNavigation(routes, initial?)`, a `MemoryNavigation<R>` with `reset(route)`, `visited` and `listeners()`. Export them from `host.ts`. `src/presentation/shell/screens.ts`: `{ screens: { settings: () => import("./index").then(m => m.SettingsScreen) }, sections: {} } satisfies ModuleScreens<"shell">`. Every module's `screens.ts` loads components only through `import()` (global constraint 5).
- [ ] **5. The composition** (`src/presentation/app-surface.ts`): `MODULE_SCREENS: { readonly [Name in AppModuleName]: ModuleScreens<Name> }`, the **second shared line** a module adds (L3); a module of `APP_MODULES` without its entry does not compile. `appSurface` merges the screens, orders the section parts by `SETTINGS_SECTIONS`, joins the modules' menu entries in module order and takes the one context area. The frame has one context area, and the type of `ModuleScreens` cannot say "at most one module fills it", so `frameContextOf(modules)` (exported with `MODULE_SCREENS`) throws at load, naming the modules, when two of them define `context`, instead of dropping the second one in silence; `tests/unit/presentation/app-surface.test.ts` fails first (the one module that fills it, the error text for two, none). It holds no other rule of its own. Update `tests/unit/application/modules.test.ts` to require `src/presentation/<name>/screens.ts` for each module. Extend `preloadSurface()` (Task 09) with `appSurface`'s start screen, context and every section's component and badge.
- [ ] **6. Vue side** (`navigation.ts`): `provideRouting(app, definition, navigation)` (returns its release), `useRouting()`, `useRoute()`, `useNavigate()`, `useHistory()` (`canGoBack`, `canGoForward`, `back`, `forward`). `mountSurface` gains the options `surface: SurfaceDefinition<R>` and `navigation: ViewNavigation<R>` and calls `provideRouting`; `content` becomes optional, and without it `ShellApp` shows `AppFrame` with `RouteOutlet`. `RouteOutlet.vue` loads the route's screen lazily, shows `NotFoundState` when `screen` returns `undefined`, and keys the screen by route **name**, so a screen with sections stays mounted across them. `NotFoundState.vue` (`data-testid="not-found"`; title, detail and a button back to the start route from `catalog.shell.notFound`) also serves a screen whose record is gone. `AppFrame.vue` (`data-testid="app-frame"`): a labelled `<nav>` with back and forward icon buttons (`data-testid="frame-history"`, shown once the history has a step; `aria-disabled` when there is nowhere to go; accessible names `frame.back`, `frame.forward`), the context slot (`data-testid="frame-context"`), one button per menu entry (`data-testid="frame-navigation"` on their list) with `aria-current="page"` on the current one (compared by route name, so "Settings" is current on every section); a labelled `<section>` with the outlet; a size container that lays the navigation out as a sidebar from 860 px of its own width and as a row below (window width plays no part; an Obsidian pane can be narrow on a desktop). Set `lang` to the UI language on the frame. Add the shell catalog's `frame` and `notFound` texts (Task 05 step 9).
- [ ] **7. `SettingsScreen.vue`** (`data-testid="settings-screen"`): a labelled `<nav>` (`data-testid="settings-sections"`, `aria-label` from `frame.settingsSections`) with one button per section, `aria-current="page"` and a bar on the current one, each in the tab order, in a row that wraps at 320 px; below it the current section; with a single section no navigation; a section id without a part shows not-found; the chosen entry keeps the focus while the section remounts. A part's `badge` loads lazily beside its label (L10).
- [ ] **8. `ShellView`** (`shell-view.ts`), constructed with `(leaf, runtime, surfaces, definition, loadSurface = importSurface)`, keeping the first four under exactly these field names: `navigation.e2e.ts` (Task 12) reads `runtime`, `surfaces` and `definition` from an open view to build a second one.
  - `navigation = false` (L23): with `true`, Obsidian records leaf history but a plain click in the file explorer (`getLeaf(false).openFile`) opens the note in the plugin's tab and the view vanishes;
  - `getViewType()` = `SHELL_VIEW_TYPE`, `getDisplayText()` = `PRODUCT_NAME`, `getIcon()` an Obsidian icon name;
  - a `memoryNavigation(definition)` per view; `getState()` = `{ ...super.getState(), route }`; `setState(state)` decodes the route: the **first** state Obsidian sets (a restored layout, `openRoute` on a new view) is `reset` and starts the history, a later one is a navigation; every route change calls `app.workspace.requestSaveLayout()`;
  - `onOpen`: register the close in `surfaces` **before** `await loadSurface()` (a view closed while the module loads never mounts), `contentEl.empty()`, then `mountSurface(contentEl, runtime, { surface: definition, navigation, elements: { host: contentEl.createDiv(), portal: contentEl.createDiv() } })`. Obsidian calls `onOpen` before `setState`, so a restored view mounts on the start route and switches in the same task, before the next paint;
  - `onClose`: remove from `surfaces` and close.
  Bootstrap's view factory becomes `(leaf) => new ShellView(leaf, runtime, surfaces, appSurface)`.
- [ ] **9. Opening from outside** (`openRoute(workspace, route?)`, `open-route.ts`): takes the first leaf of `SHELL_VIEW_TYPE`, else `workspace.getLeaf(true)`; calls `setViewState({ type, active: true, state: { route } })` on a new leaf or when a route is given; then `revealLeaf`. Without a route an open view keeps its own. The `open-view` command and the ribbon use it; a feature command passes its route.
- [ ] **10. Tests.** `tests/support/surface.ts`: `TestRoute` and `testSurface()`, a definition with test-only routes (two screens, an item with a parameter, a route without a screen); `mountTest` mounts it; `mountApp(root, runtime, options)` mounts the real `appSurface`. Navigation is proved on test routes so the plugin ships no fake screens. `navigation.test.ts` (navigate, back, forward, limit, not-found), `settings-screen.test.ts` (two sections, focus kept across sections, one section without navigation, an unknown section), `view-state.test.ts` (restore, a broken state falls back to the start, two views keep their own routes), `settings-state.test.ts` (a restored state on each section), `open-route.test.ts`, `shell-view.test.ts` (mounts once, a view closed while loading never mounts, plugin unload closes the surface before the runtime is disposed).
