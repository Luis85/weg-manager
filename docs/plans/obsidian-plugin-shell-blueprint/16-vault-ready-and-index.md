# Task 16 · VaultReady and the index

Phase B. Needs: Task 15.

**Goal.** One edge, `VaultReady`, says the metadata cache holds the frontmatter of every Markdown file the vault has now; an in-memory index of every registered note type builds from one read at that edge and follows file events by re-reading paths. Views read lists from the index, never from `NoteStore.list`. Nothing is persisted: the notes are the only store.

## Steps

- [ ] **1. Measure first, in an e2e spec, before you design around a signal** (L8). Measured in Obsidian 1.15.1 on a reference vault of 2,200 notes, 2,000 with frontmatter:
  | Situation | Obsidian | `VaultReady` |
  | --- | --- | --- |
  | cold start (never indexed) | layout ready after about 0.25 s with 1 note cached; then one note after the other (about 2 s more), each with `changed`, `resolve`, `resolved`; `resolved` fires about 2,150 times, the first before the layout is ready | on the `resolved` after the last note is indexed |
  | warm restart | every note cached at layout ready; no `changed`; `resolve` per note and one `resolved` about 25 ms later | right after `LayoutReady` |
  | plugin enabled in a running app | everything cached; Obsidian fires nothing | right after `LayoutReady` |
  So `resolved` alone is no signal and Obsidian has no public "resolved" state. Re-run the measurement with your Obsidian version (`vault-ready.e2e.ts`); if it differs, the measurement decides.
- [ ] **2. Cache completeness** (`cacheCompleteness`, `cache-completeness.ts`), public API only: complete when every file of `vault.getMarkdownFiles()` has a `metadataCache.getFileCache(file)` entry. Check at layout ready and on every `resolved` (fired after every indexed file and after a delete). A check costs a few lookups, not a scan: it remembers the files still waiting and goes on from the first one; a file deleted meanwhile no longer counts; a file created meanwhile is found by one last scan. `hostEventsLayer` publishes `VaultReady {}` once per load, always after `LayoutReady`; the `resolved` listener follows the same `registerEvent`/`offref` rules as the others; the check runs inside `publish`, so a throwing cache goes to `reportDefect`. **The deadline.** A Markdown file that never gets an entry would keep the cache incomplete and every view waiting; none was found in Obsidian 1.15.1 (null bytes, a binary `.md`, 30 MB, excluded files, symlinks and an unreadable file all got one), so this is a safety net. `hostEventsLayer` runs a fiber on its scope that waits for a sign of life, the layout being ready or a `resolved` with files still missing; when `VAULT_READY_DEADLINE` (10 s) passes without the next one, it publishes `VaultReady` anyway and logs `vault.ready.fallback` (`warn`) once with `data: { missing }`, a count, never a path. Count from the layout and from the last `resolved`, not from the start: a cold start fires a `resolved` about every millisecond, so a vault still being indexed never reaches the deadline however large; only silence does. `VaultReady` stays once per load; a file indexed after the fallback fires `changed`, and the index reads it through `MetadataChanged`. The fiber ends with the scope (unload, a failed or aborted bootstrap); a fallback that cannot read the cache reports a defect once. The double: by default every file is indexed already (warm restart, running app); `metadataCache.startCold()` re-indexes every file one per macrotask with `changed`, `resolve`, `resolved`; `resolveAll()` is what a warm restart fires; `withholdIndex(path)` is a file Obsidian never gets to (no entry, no events) until `restoreIndex(path)`; combine with `layoutReady = false` and `markLayoutReady()`. Tests: `tests/dom/infrastructure/shell/vault-ready.test.ts`; `vault-ready-fallback.test.ts` for the deadline under `TestClock` (no `VaultReady` before it, one after it, none after unload, no timer left); `tests/dom/infrastructure/notes/note-index-fallback.test.ts` (the index ready without the withheld file, which appears once indexed).
- [ ] **3. The consumer rule** (every state built from the vault): subscribe while the runtime is built (so both edges are seen; the host adapter is built last, Task 06); build from a read **at `VaultReady`**, not at `LayoutReady`; drop every event received before it (the read holds their effect; on a cold start that is one `MetadataChanged` per file); apply every later event as an **idempotent update keyed by path** that re-reads the note's current state, never a delta such as a counter, because an event published between `VaultReady` and the read is both in the read and in the stream.
- [ ] **4. The registry.** Add `noteTypes` to `ModuleManifest` and `noteTypesOf` to `module.ts`; `src/application/note-types.ts`: `appNoteTypes = noteTypesOf(APP_MODULES)`. `notes` may not import a feature, so the root composes the types. A registry entry is any `defineNoteType` result; one type name twice is a defect at build. Test: `tests/unit/application/note-types.test.ts` fails for a note type a module's domain index exports but no manifest lists.
- [ ] **5. `NoteIndex`** (`noteIndexLayer(types)`, built by `appServicesLayer` over the `noteStore` adapter for `options.noteTypes ?? appNoteTypes`):
  - **holds** per type the `editable` and `read-only` outcomes keyed by path, after `markDuplicateIds` over every type (an id is unique across types) and, once Task 15 step 11 is built, `markMissingReferences` (`src/domain/notes/references.ts`: `{ code: "reference.missing", key, id }` for each id a record's valid reference values name and no indexed record carries, one per missing id and field; the record keeps its kind, because Sync may bring the target back, and the issue is shown, never logged; a reference to a type no module registers is a defect at build), and beside them the notes of no registered type that must be shown (`UnindexedNote`): `schema.malformed` (anywhere), `schema.unknown-type` with the type (anywhere), `frontmatter.unreadable` (from `NoteStore.unreadable(rootFolder)`, under the root folder only); `describeUnindexedIssue` words them;
  - **reading**: `noteSnapshot(type)` (now, never suspends) and `noteChanges(type)` (current first, then each change), the pair `useStream` takes; the same for the unindexed notes. A snapshot is `{ ready, failure, notes, byId }`: `ready` once `VaultReady` was seen and a build succeeded; `notes` sorted by path in code-unit order; `byId` the same notes by their id, built once when the snapshot is published (`notesById`), so the record kit (Task 17) and a route such as `item/<id>` find a record without a scan (a note without a valid id is only in `notes`; an id several notes carry gives the first by path, read-only like the others); a snapshot whose status and notes did not change is not published again (an unchanged note keeps its object, so comparison is by reference except for duplicates); an unregistered type is a defect;
  - **build**: at `VaultReady`, read `list` and `unreadable(rootFolder)` once, decode, mark duplicates, publish; every command before it is dropped;
  - **follow**: a worker fiber takes file events from a queue as paths to read again: `MetadataChanged` and `FileDeleted` of a Markdown file ask for their path, `FileRenamed` for both; `FileCreated` and `FileModified` ask for nothing (they come before the cache holds the new state, and `MetadataChanged` follows); each path is re-read with `NoteStore.read`; a record replaces what is held there, a note that is gone (`NoteNotFoundError`) or no record loses it, and a path under the root folder that reads as no record is checked against `unreadable`;
  - **batches**: a batch closes after `INDEX_BATCH_QUIET` (100 ms) of quiet or `INDEX_BATCH_MAX` (1 s) after its first event, so a sync of many files is one publish and a long sync still shows progress once a second; duplicates are re-marked after each batch;
  - **own writes**: the store's writes do not notify the index; the writer's view waits for the event like every other view, so one path serves own writes and outside edits and no stale read can overwrite a written note (L9);
  - **rebuild** (`rebuildNoteIndex`): reads everything again and resolves once the new snapshots are published; one asked before `VaultReady` waits for the first build; a change of `rootFolder` rebuilds; a rebuild ends the collecting batch;
  - **failure**: a failing `list`, `read` or `unreadable` never stops the index; the snapshot keeps the notes read last and sets `failure` to `NoteIndexReadError`, cleared only by a rebuild that succeeds; a failed first build is `ready: false` with `failure` and no notes; a defect in a build or a batch goes to `reportDefect` once and the index goes on;
  - **lifecycle**: queue, fibers and subscription live in the runtime's scope; after `dispose()` nothing is read or published, a pending rebuild is interrupted, a later one returns at once;
  - **logs**: `notes.index.built` (`info`, counts), `notes.index.build.failed` and `notes.index.read.failed` (`warn`); counts only.
