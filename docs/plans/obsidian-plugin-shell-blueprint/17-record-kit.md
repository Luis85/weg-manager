# Task 17 · The record kit

Phase B. Needs: Task 16.

**Goal.** What every record type needs beyond the codec lives in `notes`, in every layer, before any feature exists (L22). A feature then declares its note type, its rules, its texts and its layout, and gets lists, writes, the form's flow, the conflict UI, the delete dialog and the data issues section from `notes`.

## Files

Domain (`src/domain/notes/`): `file-name.ts` (`recordFileName`, `fitsFileName`, `MAX_FILE_NAME_BYTES`, `followsTitle`), `form.ts` (`FormInput`, `FormDraft`, `trimmedValues`, `editedValues`), `lineOfText` and `isControlCharacter` in `fields.ts`. Application (`src/application/notes/`): `record-kit.ts` (`defineRecords`), `record-list.ts` (`RecordRow`, `RecordList`, `fileNameOf`), `folders.ts` (`recordFolder`, `isInFolder`), `routes.ts` (`DATA_ISSUES_SECTION = "data-issues"`), `describeRecordIssue` and `RecordTexts`, `IssueSentences` in `i18n/`. Presentation (`src/presentation/notes/`): `index.ts`, `screens.ts`, `use-record-form.ts`, `use-record-screen.ts`, `focus-after.ts` (`useFocusAfter`, `cardKey`), `conflict.ts`, `components/{ConflictChoice,DeleteRecordDialog,OpenNoteButton,DataIssues,DataIssuesBadge}.vue`. Tests: `tests/unit/domain/notes/{file-name,form}.test.ts`, `tests/unit/application/notes/{record-list,record-writes,record-update,record-texts,records}.test.ts`, `tests/support/notes/record-fixture.ts` (a sample type `sampleType` and `samples = defineRecords(…)`), `tests/dom/presentation/notes/{data-issues,index-failure}.test.ts`. Modify: the notes manifest (`sections: [{ id: DATA_ISSUES_SECTION, order: 900 }]`), `src/presentation/notes/screens.ts` (the section, step 8), `tests/unit/application/routes.test.ts` (`SETTINGS_SECTIONS` gains `data-issues`), `configs/fallow.config.mjs` (the rule `presentation/notes` of the Task 03 table), `src/styles/app.css` (each new Nuxt UI component: `Modal`, `Slideover`, `FormField`, `Input`, …).

Install: `@tanstack/vue-form` (`dependencies`; `useRecordForm` is its first user). From now on `tests/dom/lazy-presentation.test.ts` also finds it unevaluated at plugin load.

## Steps

- [ ] **1. File names** (domain, tests first in `file-name.test.ts`): `recordFileName(title, fallback)`: the title with each run of `\ / : * ? " < > | # ^ [ ]` and control characters replaced by one hyphen, white space collapsed, leading and trailing dots and spaces dropped, `fallback` when nothing is left. `fitsFileName(title, fallback)` with `MAX_FILE_NAME_BYTES = 255`: the file name `recordFileName` gives, with the longest clash suffix ` (100)` and `.md`, has at most 255 bytes in UTF-8 (the limit of Linux and macOS; Windows counts 255 UTF-16 units, never more than the bytes); 100 CJK characters are 300 bytes, so test with three-byte characters. A feature checks it at its title field for a new or changed title only (the tracer's `title.too-long`, Task 18), so a name that is too long is an issue there, never a failed write; a title a record already has is not checked, so a note named so outside the plugin keeps working and is not renamed while its title stays. `followsTitle(fileName, title, fallback)`: the file still carries that name, also with a clash suffix ` (n)`, compared by `clashKey`. A name the user gave the file by hand stays.
- [ ] **2. Form values** (domain, `form.test.ts`): `lineOfText(max)` (one line of text, no control character, at most `max`); `trimmedValues(input)`; `editedValues(type, input, draft, loaded)`: a field whose input is still the loaded text keeps the note's valid value as written, surrounding spaces included, so an untouched field is never rewritten.
- [ ] **3. `defineRecords({ type, title, fallbackName, log, issue?, between? })`** (application). Tests first on the sample type (`record-list.test.ts`, `record-writes.test.ts`, `record-update.test.ts`) with `tests/support/notes/record-fixture.ts` (the index over the sample type, a sequential id generator, `ready`, `indexed`, `stored`, `storedPaths`, under `TestClock`). It gives:
  - `list` and `changes` (a `RecordList` of `RecordRow`: path, file name, id, `editable`, valid values, issues, frontmatter), sorted by title with `localeCompare(…, "<collation-language>", { numeric: true })` and path second; `issue` adds the data a sentence needs to the codec's issue; `between` adds issues between records over the sorted rows (for example a duplicate title); `toList`; `shownName` (the title, else the file name);
  - `create(values)`: an id from `IdGenerator`, the note in `recordFolder(rootFolder, type)` named by `recordFileName`, a taken name with ` (2)`;
  - `update(row, values)`: `NoteStore.update(path, editChange(type, row.frontmatter, values))`, then the file follows the title while `followsTitle` holds for the old name, up to ` (100)`; save and rename run **uninterruptibly as one command**; a rename that fails keeps the saved note and logs `<log>.rename.failed` (`warn`, no data);
  - `remove(row)`: `NoteStore.trash`;
  - update and remove find a note renamed meanwhile **by its id**; while another note carries the same id, both are read-only and a write fails `NoteWriteRefusedError { reason: "duplicate-id" }`;
  - every successful write is confirmed by an `info` notice from the notes catalog (`notices.created`, `saved`, `deleted`, by the title): a toast confirms a short-lived success; a failure stays at the form.
- [ ] **4. Texts** (`record-texts.test.ts`): `describeRecordIssue(issue, notes, texts)` words a feature's issues from its `RecordTexts` (`fields` labels, optional `missing`, `issues: IssueSentences<Issue>`); the record issues and field kinds' codes are the notes catalog's. The generic texts (notices, conflict, delete dialog, "Open in Obsidian", data issues) carry no feature words.
- [ ] **5. `useRecordForm({ type, record, initial, create, update, invalid, rules, describe, labels, summary, root, done })`** (presentation, TanStack Form). The options: `type` the note type; `record` the `RecordRow` being edited, `undefined` to create one; `initial` start values of a new record beside the empty ones; `create(input)` and `update(row, input)` the feature's use cases as `UseCaseFn`s, each resolving to the note as written (`{ frontmatter }`); `invalid` the `_tag` of the feature's error whose `issues` land at their fields (the tracer's `InvalidItemError`); `rules(input)` the feature's rules for the input as it stands; `describe(issue)` an issue in the feature's words (`describeRecordIssue` with its texts); `labels` each field's label, which the conflict's legend uses; `summary` the `{ title, detail }` a failed submit shows at the top of the form; `root()` the form's root element, in which the focus moves to the first field with `aria-invalid`; `done(id)` called with the id of the record that was saved. It gives: validators that call the feature's `rules` (which call the domain rule, global constraint 15); the use case's issues placed at their fields; a failed submit shows a summary with `role="alert"` at the top and moves the focus to the first field with `aria-invalid`; the note's own issue shown at its field until the field changes; Save `aria-disabled` while blocked, never `disabled` (L30); **the conflict loop**: on `NoteEditConflictError` the form shows `ConflictChoice` with, per field, the value when the form opened, the user's and the note's current one; the user picks one per field; applying ends the conflict view, a chosen value that breaks a rule stays in the form with its issue, and the next save goes against the same current values (the conflicting fields of `loaded` replaced by `current`). The conflict takes the focus to its heading (`tabindex="-1"`).
- [ ] **6. `useRecordScreen({ type, list, root })`**: the folder for the intro text, loading only after 300 ms (`useDelayed`), the index's failure with a retry (`ErrorNotice` with `rebuildNoteIndex`; `tests/dom/presentation/notes/index-failure.test.ts`), the empty state, the sheet and the delete dialog with their modal props (`useModal`), and the focus after them (`useFocusAfter`): to the saved or created card's edit button once the index shows the card (else its heading), back to the opener on cancel, to the create button once a deleted card has left the list. Cards carry `data-card-key` = `cardKey(row)` (the id, or the path for a note without an id of its own) so a card survives the rename of its file; focus targets carry `data-focus="edit" | "remove" | "name" | "add"`.
- [ ] **7. Components.** `DeleteRecordDialog` (a `UModal` that asks first, initial focus on Cancel, runs the feature's delete as a command, title from the feature, the rest from the notes catalog); `OpenNoteButton` ("Open in Obsidian" through `openNote`, on every read-only record and every data-issue note, so a note the plugin cannot write can be repaired by hand); `ConflictChoice`.
- [ ] **8. The data issues section.** `DataIssues.vue` lists the unindexed notes (`unindexedChanges` with `useStream`, worded by `describeUnindexedIssue`, each with `OpenNoteButton`); `DataIssuesBadge.vue` counts them beside the section's label. `src/presentation/notes/screens.ts`: `{ screens: {}, sections: { "data-issues": { label, component: () => import("./components/DataIssues.vue"), badge: () => import("./components/DataIssuesBadge.vue") } } } satisfies ModuleScreens<"notes">`. Test: `tests/dom/presentation/notes/data-issues.test.ts` (the section, the app's navigation with its badge; the badge arrives after the list, so wait for it, L10). Whether readable records with an issue of their own (a duplicate id, a newer version) are also listed here is decided with the second record type.
