# Task 05 · Shell domain and application

Phase A. Needs: Tasks 03 and 04.

**Goal.** The shell's pure rules and services: settings that decode per field, migrate in memory and never get damaged; writes that run to completion; logs and diagnostics typed so they cannot leak note content; one catalog part per module and language; and an error text for every tagged error by construction.

## Files

Create in `src/domain/shell/`: `settings-codec.ts`, `settings.ts`, `index.ts`. In `src/application/shell/`: `ports.ts`, `errors.ts`, `settings-service.ts`, `logger.ts`, `logged-error.ts`, `defects.ts`, `diagnostics.ts`, `use-cases.ts`, `commands.ts`, `services.ts`, `i18n/describe.ts`, and fill what Task 03 started: `user-messages.ts`, `module.ts`, `index.ts`, `i18n/{catalog,<language>}.ts`. At the application root: `errors.ts` (`AppError`), `messages.ts`, `user-messages.ts` (`describeError`), `commands.ts` (`appCommands`). Tests in `tests/unit/domain/shell/` and `tests/unit/application/shell/`, plus `tests/support/layers.ts`. Modify: `configs/fallow.config.mjs` (the zones `domain` and `application-describe-error`, the rules `domain`, `domain/shell` and `application-describe-error`, and `domain` in the rules `application` and `application-composition`; Task 03 table), then `npm run fallow:config`.

Install: `effect` (`dependencies`); `@effect/vitest`, `fast-check` (`devDependencies`).

## Steps

- [ ] **1. The settings codec** (`src/domain/shell/settings-codec.ts`). Tests first with a test-only declaration set (`tests/unit/domain/shell/settings-codec.test.ts`), then `makeSettingsCodec({ version, fields, migrations })` returning `decode`, `encode`, `validatePatch`:
  - **A declaration per setting**: the Effect Schema that reads a raw JSON value into the in-memory one (trimming and legacy values live in the schema), the `default`, the `issue` a rejected value produces, and `omitWhenDefault`. A type `SettingsFields<Editable, …>` fails typecheck for a missing or misspelled declaration.
  - **Decode never throws.** Missing or `null` file: defaults, no issue. A non-object: defaults and `file.invalid`. A field the schema rejects falls back to its default alone and reports its issue; the other fields keep their values. Unknown keys are dropped. A newer `schemaVersion`: defaults, `schema.newer` with the version, read-only (`readOnlyReason: "newer-version"`). A version that is not a positive integer: `schema.invalid`, decoding goes on. A missing version counts as current.
  - **Migrations** (`Migrations = { [from]: (raw) => raw }`, `runMigrations`): applied in order from the file's version up to the current one, before the field decode, **in memory only** (L29). A step that throws or returns no object: defaults, `migration.failed` with its version, read-only (`readOnlyReason: "unreadable"`), so no save replaces the old values with defaults.
  - **Encode** writes the version and every field except a default marked `omitWhenDefault`, so an older plugin on another device reads the file without an issue.
  - Property test (fast-check, `fc.anything()`): decode never throws; decoding the encoded result gives the same settings and no issue.
- [ ] **2. The shell's settings** (`src/domain/shell/settings.ts`): `SETTINGS_VERSION = 1`, `MIGRATIONS = {}`, `LOG_LEVELS = ["error", "warn", "info", "debug"]`, `FIELDS = { logLevel: { schema, default: "warn", issue: { code: "logLevel.unknown", allowed: LOG_LEVELS } } }`, `SettingsIssue` (an Effect Schema union of the structural issues and `logLevel.unknown`), `DEFAULT_SETTINGS`, `decodeSettings`, `encodeSettings`, `validatePatch`. Task 13 adds `rootFolder`. Tests pin each exact issue (`settings.test.ts`, `settings-properties.test.ts`, `settings-compat.test.ts` for real-shaped old files).
- [ ] **3. Ports** (`src/application/shell/ports.ts`), each a `Context.Service` class keyed `"<plugin-id>/application/<Name>"`: `SettingsStore` (`load`, `save`; both may fail `StorageError`), `Notifier` (`notify(message: UserMessage)`), `Logger` (`log(entry)`, `recent`), `LogSink` (`write(entry)`), `Incidents` (`nextId`), `Clipboard` (`write(text)`, may fail `ClipboardError`), `HostInfo` (plugin version, API version, platform, a plain value), `Messages` (the whole `Catalog` of this load's language, typed from the root as a type only).
- [ ] **4. Errors** (`errors.ts`), each `Schema.TaggedError`: `StorageError`, `ReadOnlySettingsError { reason: "newer-version" | "unreadable" }`, `InvalidSettingsError { issues }`, `VaultReadError`, `ClipboardError`; `ShellError` is their union. Name every tag in the manifest (`errors: { tags: { StorageError: true, … }, describe: describeShellError }`); typecheck fails while one is missing (`ErrorTags`, Task 03).
- [ ] **5. `SettingsService`** (`settings-service.ts`). Tests first, `it.effect` from `@effect/vitest`, over the in-memory store of `tests/support/layers.ts` (`inMemoryStore` with `holdSaves`/`releaseSaves`/`heldSaves`, `setFailSave`, and `uncancellableSaves: true` modelling `plugin.saveData`):
  - `current`, `status` (`writable`, `issues`, `readOnlyReason`), `changes` and `statusChanges` (each emits the current value first, then every change; two `SubscriptionRef`s), `update(patch)`, `reload`.
  - A load problem shows one notice and leaves the store untouched; nothing is saved until `update`.
  - A read-only file is never written: `update` fails `ReadOnlySettingsError`.
  - **Save-then-set is uninterruptible** (L4): an update that has started its save always sets the settings too, even when its caller is interrupted. `tests/unit/application/shell/settings-interruption.test.ts`: interrupt an update while an uncancellable save is held; after release, disk and memory are equal. Waiting for an earlier update stays interruptible.
  - `reload` reads the file again and decodes it as on load; unchanged values publish nothing; a notice appears only when the status changes; reloads and updates are serialised (`settings-reload.test.ts`).
  - The service does not log: the logger depends on it for its level.
- [ ] **6. Logging** (`logged-error.ts`, `logger.ts`). An entry is `{ level, event, data?, error?, incidentId? }`: `event` a stable dotted name (`settings.load.failed`, `plugin.loaded`, `defect.reported`), `data` only `number | boolean` values, `error` a `LoggedError`. `toLoggedError(cause)` is the only way to put a cause in an entry: `name` (a plain identifier of at most 64 characters, else `Error`; `NonError` for a non-`Error`), `message` (raw, for the console sink only), `frames` (at most 10, each the function name if made of code characters and the file's last path segment with `:line:col`; V8 and JavaScriptCore/Firefox frame formats; every other line dropped). `LoggerLive({ developmentMode })` filters by the `logLevel` setting (everything in development mode), follows `changes` without a reload, and keeps the last 50 accepted entries for diagnostics. Tests: `logged-error.test.ts`, `logger.test.ts` (L5).
- [ ] **7. Defects** (`defects.ts`). `reportDefect(cause)`: one `error` entry `defect.reported` with `toLoggedError(cause)` and a six-character incident id (0–9, A–Z, from `Incidents`; sequential `T-1`, `T-2` in tests), one notice `describeDefect(id, messages.shell)`, returns that message. `reportUnexpected(cause)`: silent for an interruption, otherwise `reportDefect` once with `Cause.squash`; `Effect.catchCause(reportUnexpected)` is how boundaries guard an effect (Tasks 06, 07, 09).
- [ ] **8. Diagnostics** (`diagnostics.ts`, use case `copyDiagnostics`). A plain-text report: plugin version, API version, platform, UI language, settings status and issues, log level, the last 50 entries, each with timestamp, level, event, incident id, `data` as JSON and the error's `name` with its frames, one per line. Never `message`. No redaction step: the report is an allow-list by type (L5). The report stays in one fixed language, the fallback language of `<languages>` unless the product names another, so support reads one format; only the confirmation notice follows the UI language. `copyDiagnostics` notifies success or `describeError(ClipboardError)`. Tests: `diagnostics.test.ts` pins the exact format; `diagnostics-leaks.test.ts` runs defects (also non-`Error` causes and causes whose message names a path) through the report with fast-check and finds neither the message nor any directory of a stack location.
- [ ] **9. Catalogs and texts.** Per module `src/application/<module>/i18n/catalog.ts` (the module's catalog type), one file per language typed by it, and `describe.ts` (issue codes into sentences). Texts with parameters are functions. Rules: cause first, then the action; no reassurance texts; one form of address per language, chosen once for the product (for example the informal second person in German, *du*, and sentence case in English as Obsidian writes it); a text that asks the user to report a problem names the plugin's GitHub issues and carries `link: ISSUES_URL` (`ISSUES_URL = "https://github.com/<owner>/<repo>/issues"`, one constant in `src/application/shell/i18n/catalog.ts`), never inside `detail`, which stays free of `/`. `PRODUCT_NAME = "<Plugin Name>"` is the same in every language. Root `messages.ts`: `type Catalog = CatalogOf<AppModule>`, one constant per language from `catalogOf(APP_MODULES, language)`, `catalogFor(language)`, `languageFromCode(code)` (each non-fallback language of `<languages>` matches its code and any `-*`/`_*` region variant case-insensitively, everything else is the fallback), `messagesLayer(language)`. The shell's catalog (`ShellCatalog`) holds: `language`; `issues` (one sentence function per `SettingsIssue` code); `errors` with `storage`, `readOnly` (`title`, `detail` per `ReadOnlySettingsError` reason), `invalidSettings` (`title`), `vaultRead`, `clipboard` (each `{ title, detail }` unless named); `defect` (`title`, `detail(incidentId)`); `settingsReset` (`title`, `detail(issues)`); `diagnosticsCopied`; `actions` (one label per `UserMessageAction`); `commands` (`openView`, `copyDiagnostics`); `settingsTab.logLevel` (`name`, `desc`, `labels` per log level). Task 09 adds `notFound` (`title`, `detail`, `back`), Task 10 `frame` (`navigation`, `settings`, `content`, `back`, `forward`, `settingsSections`). Tests: `tests/unit/application/shell/i18n.test.ts` pins every shell text in every language and compares the catalogs' key shapes.
- [ ] **10. Error texts.** `describeShellError(error, messages)` is exhaustive over `_tag` (a `switch` the ESLint rule checks), with severity and `action` (`retry`, `open-settings`, `copy-diagnostics`) fixed per tag, independent of language. Root `src/application/errors.ts`: `type AppError = ErrorOf<AppModule>`; root `src/application/user-messages.ts`: `describeError = describerOf(APP_MODULES)`. `UserMessage = { severity: "info" | "warning" | "error", title, detail, action?, link? }` with `UserMessageAction = "retry" | "open-settings" | "copy-diagnostics"`. Tests: `tests/unit/application/shell/user-messages.test.ts` with the exact text per tag in each language and a property test (fast-check strings as causes) that no message contains `Error`, `stack`, `/`, `\` or the cause's text.
- [ ] **11. Commands.** `PluginCommand<Messages, Route, R> = { id, name(messages), action }` with `action` `{ _tag: "open", route? }` or `{ _tag: "run", effect }` (a use case that handles its expected failures itself, as `copyDiagnostics` does). `shellCommands`: `open-view` (open, no route: an open view keeps its route) and `copy-diagnostics` (run). Ids are kebab-case without the plugin id, which Obsidian adds. Add `commands` to `ModuleManifest` and `commandsOf` to `module.ts`; root `src/application/commands.ts`: `type AppCommand = PluginCommand<Catalog, Route, AppServices>` and `appCommands: readonly AppCommand[] = commandsOf(APP_MODULES)`. Neither `Route` nor `AppServices` exists yet: write `never` for the route until Task 10 and `ShellServices` for the services until Task 06; those tasks put in the real types. Test: `tests/unit/application/commands.test.ts` with the ids and labels in each language.
- [ ] **12. Use case `setLogLevel`** for the settings tab of Task 07. No other shell use case: a setting with a UI elsewhere would break the one-edit-location rule.
