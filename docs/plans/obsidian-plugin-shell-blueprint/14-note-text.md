# Task 14 · Line edits and the YAML writer

Phase B. Needs: Task 13.

**Goal.** `NoteStore.update` changes only the frontmatter lines of the keys it sets or removes and leaves every other byte of the file as the user or another tool wrote it: comments, unknown keys in their form, quoting, order, line breaks, a BOM, the body. When it cannot be sure, it writes nothing and says why.

Why not `fileManager.processFrontMatter`: it parses the whole YAML block and writes all of it back. In Obsidian 1.15.1 saving a record after changing one key turned `plz: 01067` into `1067`, `version: 1.10` into `1.1`, rounded a 20-digit number, dropped a comment, rewrote `[a, b]` as a block list, unquoted `'yes'`, saw no block after a BOM (so a BOM note was listed but every save refused), and wrote LF lines into a CRLF note (L6). Why not `getFrontMatterInfo` to find the block: it sees no block after a BOM or with lone carriage returns and does not close at `----`, while the metadata cache does (L7).

## Steps

- [ ] **1. `update(path, change)`** on the port: `change` receives the current frontmatter inside the atomic write and returns a patch (`set`, `remove`) or a typed failure that aborts the write; a patch that changes nothing writes nothing; what `change` throws is a defect and writes nothing. The Obsidian adapter calls `vault.process(file, fn)`: Obsidian hands `fn` the file's text as it is at that moment, BOM and line breaks included, and writes what `fn` returns, or nothing when it returns the same text. Inside `fn` runs `updateNoteText(text, change, parseYaml)`, which is pure and takes Obsidian's `parseYaml` as an argument. A note deleted between lookup and write makes `vault.process` reject with ENOENT without calling back; report `NoteNotFoundError` when the file is no longer at its path. The double's `process` does the same (hands over the raw text; writes and fires `modify` only on a change; a callback's throw rejects unchanged; a file deleted meanwhile rejects with ENOENT without calling back).
- [ ] **2. Split** (`splitNoteText`) where the metadata cache splits, as measured in Obsidian 1.15.1: after one BOM, a first line `---` (LF or CRLF), up to the next line that starts with `---`. No such line is no block. Measured there: the cache closes the block at **every** line that starts with `---`, whatever follows (`----`, `-----`, `---- `, `--- x`, `---x`, `--- # c`), with LF or CRLF; ` ---` and `...` do not close it. The update writes into a block closed by `---`, by `---` with spaces or tabs after it, or by `----`, and keeps that closing line byte for byte (owner decision of 2026-11-22, PBI-65 in the source). Every other closing line, lone carriage returns and an opening line other than `---` are refused with reason `layout`. Record the closing-line facts in the fidelity scenarios (`vaultFacts`), so the double and Obsidian are compared on them.
- [ ] **3. Read** the block with `parseYaml`: broken YAML or YAML that is no map is `NoteUnreadableError` (without the parser's message, which quotes the note); no block or an empty one is `{}`. Then `change` decides on a copy.
- [ ] **4. Edit lines** (`editNoteText`): find each top-level key line (plain, `"quoted"` or `'quoted'`) and the lines that continue it (indented lines, block lists also at column 0, block scalars, blank and comment lines between them). A set key's lines are replaced in place; a new key goes before the closing fence; a removed key's lines go; a block left with no line goes with its fences, as Obsidian does. New lines take the opening fence's line break (or the file's first one). A key set to the value it has is left alone. **A comment at the end of a written key line stays** (decided 2026-11-22): it goes behind the new value with the blanks the user put before it (`kind: WEG # Art` → `kind: Haus # Art`); a value that becomes a block list keeps it on the key line (`tags: # Liste`, then the items). `src/domain/notes/line-comment.ts` finds it: a `#` starts a comment only after a space or tab and outside quoted text, and quoted text starts only where a value starts, so `"A # B"`, `[a, "b # c"]` and `A#B` hold none; comments on further lines of a multi-line value belong to that value and are replaced with it; a value whose quotes do not close on the key line has no comment there; a removed key takes its lines and their comments along. Any other top-level line (a flow mapping, `? key`, `&anchor key`), and keys found by line that differ from the keys YAML read, is `layout`.
- [ ] **5. Check** (the safety net): `parseYaml` of the edited text must read exactly what `applyPatch` makes of the frontmatter before, key order included, every value equal by `Object.is`. Otherwise nothing is written: `NoteWriteRefusedError` (Task 15 defines it), reason `layout`, whose text asks the user to write the properties one per line. A save that changes nothing succeeds also for these notes.
- [ ] **6. One serialiser** (`yamlEntry`, used by `create` through `newNoteText` and by every update). Text is written plain only where YAML 1.2 (Obsidian) and YAML 1.1 (older tools an agent may use) read it back as that same text; `01067`, `1.10`, `yes`, `12:30`, `""` and text with `: `, ` #`, an indicator first, or spaces around are double-quoted; characters that are not printable or that some reader takes as a line break (NEL, LS, PS, BOM) are escaped. Dates stay plain, as Obsidian writes them. A nested map or `undefined` is a defect: no record holds one.
- [ ] **7. The two other decided fixes** (2026-11-22; they can hit a real vault):
  - **Folders are found by `clashKey`.** `create` finds its folder segment by segment the way names clash (NFC, then lower case), the type's subfolder too, and writes the path in the vault's spelling: the folder spelled exactly as asked, else the first by code unit among those that clash; from the first segment the vault lacks, the rest is created as asked. `unreadable` finds its folder the same way, and the index looks for unreadable notes in the root folder by `clashKey`. Before, a vault with `my notes/` and the setting `My Notes` got a second folder on Linux and, reasoned from Obsidian's source, a failed create on Windows and macOS. The written path still goes through `normalizePath`, so a folder stored in NFD (macOS) is matched but written in NFC; whether Obsidian on macOS then finds the same folder is not verified. Contract cases in `tests/support/notes/contract-folders.ts` (a root folder and its subfolder in another case, the exact one first among several, `unreadable` in the same folder); the check on Windows and macOS is a manual item.
  - **File names are at most 255 bytes in UTF-8**, with the longest clash suffix ` (100)` and `.md` (`fitsFileName`, `src/domain/notes/file-name.ts`; the limit of Linux and macOS; Windows counts 255 UTF-16 units, never more than the bytes). 100 CJK characters are 300 bytes. A feature checks it at its title field (Task 17), so a name that is too long is an issue there, never a failed write. A title a record already has is not checked, so a note named so outside the plugin keeps working and is not renamed while its title stays. Test with three-byte characters.
- [ ] **8. Tests, all first:**
  - `tests/unit/domain/notes/note-text.test.ts` and `yaml-text.test.ts`, with fast-check properties: every written value reads back exactly (through the `yaml` package in 1.2 and 1.1 mode); on generated notes every byte outside the patched keys stays;
  - `tests/unit/application/notes/note-text.test.ts`: split, read, edit, check, each refusal reason, the two closing-line variants, the kept trailing comment;
  - the byte-fidelity group of `obsidian-note-store.test.ts` on the double: a note with comments, `01067`, `1.10`, a 20-digit number, a flow list, `'yes'`, a quoted key with a comment, a list at column 0 and a block scalar, changed in one key, compared byte for byte; a BOM note keeps its BOM; a CRLF note is written with CRLF;
  - `note-write-fidelity.e2e.ts`: 900 generated serialiser lines read back exactly by Obsidian's own `parseYaml` (special numbers included); the block found where the metadata cache finds one (BOM, CRLF, fences, the two closing variants).

`npm run verify` exits 0 and `xvfb-run -a npm run test:e2e` exits 0. Discriminating check: let the adapter write through `fileManager.processFrontMatter`; the byte-fidelity group fails on every kept form. Commit `feat: line edits through vault.process and one YAML writer`.
