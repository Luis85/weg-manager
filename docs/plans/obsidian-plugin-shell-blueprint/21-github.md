# Task 21 · GitHub workflows and dependency updates

Phase D. Needs: Task 20.

**Goal.** CI runs the same gate as the developer's machine; e2e runs in real Obsidian beside it; mutation runs nightly; a release is built read-only from `main`, started by hand or by a tag, and published by a job that runs no repository code. All logic stays in npm scripts; the YAML only installs Node and calls them. The agent writes the files; the human enables them (steps at the end).

## Files

Create: `.github/workflows/ci.yml`, `.github/workflows/nightly-mutation.yml`, `.github/workflows/release.yml`, `.github/dependabot.yml`, `.github/pull_request_template.md`, `configs/eslint.scanner.config.mjs`, `docs/engineering/github-setup.md`, `docs/engineering/releasing.md`. Modify: `package.json` (script `lint:scanner`).

## Action pins

Pin every action by its full commit SHA with the tag as a comment (`uses: actions/checkout@<sha> # v7.0.1`); a tag can be moved, a SHA cannot; never write `@v7`. The pins this plan was verified with on 2026-11-22: `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`, `actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0`, `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2`, `actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2`, `actions/cache@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0` (also `actions/cache/restore` and `actions/cache/save` at the same SHA), `actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2`. Re-resolve each with `git ls-remote https://github.com/<owner>/<action> refs/tags/<tag>` and use the newest release whose inputs these workflows use unchanged.

## Steps

- [ ] **1. `ci.yml`** (`name: CI`, so the checks read `CI / verify`, `CI / e2e`): on push to `main` and every pull request; `permissions: contents: read`; `concurrency` with `group: ci-${{ github.event_name == 'pull_request' && github.ref || github.sha }}` and `cancel-in-progress` only for pull requests: a pull request has one group, so a newer push cancels its older run; every push to `main` has a group of its own, so none is cancelled and none waits behind another (in one group GitHub keeps a single pending run and drops the pending one when a newer arrives, so the middle one of three quick merges would get no run). Jobs, each `runs-on: ubuntu-latest` with a `timeout-minutes` (`verify` 20, `e2e` 15), each `actions/checkout` with `persist-credentials: false` (no job pushes, so none needs the token left in `.git/config` for the install scripts to find), `actions/setup-node` with `node-version-file: .nvmrc` and `cache: npm`, `npm ci`:
  - `verify`: `npm run verify`; upload `reports/junit.xml` and `reports/coverage/cobertura-coverage.xml` as `reports` when not cancelled, and `dist/` as `plugin`; then, as the job's **last step**, `npm run lint:scanner` (`if: !cancelled()`, `continue-on-error: true` on the step, and a `::warning` annotation when its outcome is `failure`): it approximates the community directory's source scan and never blocks. A step, not a job of its own, so it shares the install (CI runs `npm ci` twice per run, in `verify` and `e2e`); last, so the reports and the build are uploaded first.
  - `e2e`: resolve the Obsidian versions for the cache key (`node tests/e2e/wdio.conf.mts | grep 'obsidian-cache-key:' > obsidian-versions-lock.txt`, then `rm -rf .obsidian-cache`); restore `.obsidian-cache` with `actions/cache/restore`, key `obsidian-cache-${{ runner.os }}-${{ hashFiles('obsidian-versions-lock.txt') }}` and no `restore-keys` (a run restores the current entry or nothing, so an old version is never carried into a new entry); run `xvfb-run -a -s "-screen 0 1280x1024x24 +extension GLX -noreset" npm run test:e2e` with `WDIO_MAX_INSTANCES: 2`: `xvfb-run` is on the `ubuntu-latest` image, so nothing is installed with `apt-get` and no window manager runs (the specs wait on conditions, Task 12, so none needs a managed window; if the job stays unreliable all the same, put one back: install `herbstluftwm`, start `Xvfb :99 … &` and `DISPLAY=:99 herbstluftwm &`, write `DISPLAY=:99` into `$GITHUB_ENV`, run plain `npm run test:e2e`); then, `if: always()` and only on a cache miss, check that the download is complete (an `*.asar` in `.obsidian-cache/obsidian-app/`, an `Obsidian-*` under `obsidian-installer/*/`, a file under `electron-chromedriver/*/`, each a folder the launcher fills through a temporary one and a rename) and only then save it with `actions/cache/save` under `cache-primary-key`, so a run whose tests fail keeps its download for the retry, a hit is never saved again, and an incomplete entry, which every later run would restore and none could replace, is never written; upload `reports/e2e/` on failure. The download stays in the Actions cache, never in an artifact (Obsidian's terms forbid redistribution). The cache holds the current entry and the previous one until GitHub evicts it (about 1.3 GB unpacked each); write that count in `github-setup.md`.
- [ ] **2. `lint:scanner`** (`configs/eslint.scanner.config.mjs`, a flat config built with `defineConfig` and `globalIgnores` from `eslint/config`). It approximates the Obsidian community directory's source scan as documented for `eslint-plugin-obsidianmd@0.6.0` in the section *Community plugin scanner configuration* of https://raw.githubusercontent.com/obsidianmd/eslint-plugin/0.6.0/docs/configuration.md (the npm package does not ship that file; re-read it for a newer version). Nothing of the plugin's own ESLint config goes in: no Vue rules, no ignore of agent tooling. In this order:
  - `languageOptions.parserOptions: { projectService: true, tsconfigRootDir: <repository root> }`, then `...obsidianmd.configs.recommended`;
  - for `**/*.{ts,cts,mts,tsx,js,cjs,mjs,jsx}`: errors for `no-eval`, `no-unsanitized/method`, `no-unsanitized/property`, `obsidianmd/regex-lookbehind`, `obsidianmd/no-forbidden-elements`; off: `no-undef`, `@typescript-eslint/no-unsafe-member-access`, `@typescript-eslint/no-unsafe-assignment`, `@typescript-eslint/no-unsafe-argument`, `@typescript-eslint/no-unsafe-call`, `@typescript-eslint/no-unsafe-return`, `@typescript-eslint/restrict-template-expressions`, `@typescript-eslint/no-base-to-string`, `import/no-unresolved`, `obsidianmd/commands/no-command-in-command-id`, `obsidianmd/commands/no-plugin-id-in-command-id`;
  - `no-implied-eval: "error"` for JS files, `@typescript-eslint/no-implied-eval: "error"` for TS files;
  - JS files (`**/*.{js,cjs,mjs,jsx}`) without type information: `extends: [tseslint.configs.disableTypeChecked]`, `parserOptions: { projectService: false, project: null }`, every rule of `obsidianmd.ruleConfigs.recommendedTypeChecked` off;
  - `obsidianmd/validate-manifest` off for `manifest.json` and `obsidianmd/validate-license` off for `LICENSE`, `LICENSE.md`, `LICENSE.txt` (the scanner checks them separately);
  - `linterOptions: { reportUnusedDisableDirectives: "off", reportUnusedInlineConfigs: "off" }`;
  - ignored: what git does not track (`git ls-files --others --directory`: the scanner sees a clone), tracked `.js` files outside `src/` that look bundled (a banner such as `bundled by` or `generated by` in the first 500 bytes, or 500 bytes with fewer than two line breaks), `main.js`, `**/*.min.js`, `**/{dist,build,out,release}/**/*.{js,cjs,mjs,jsx}`, and the scanner's fixed list: `node_modules`, `dist`, `build`, `pkg`, `test-vault`, `.obsidian`, `**/.obsidian/**`, `esbuild.config.mjs`, `version-bump.mjs`, `**/*.test.*`, `**/*.tests.*`, `**/*.spec.*`, `**/*.specs.*`, `**/test/**`, `**/tests/**`, `**/__tests__/**`, `**/mocks/**`, `**/__mocks__/**`, `**/*.cjs`, `**/*.mjs`, `**/*.cts`, `**/*.mts`, `**/vite*`, `**/scripts/**`, `**/docs/**`, `**/i18n/**`, `**/i18next/**`, `**/locale/**`, `**/locales/**`, `**/translations/**`, `**/l10n/**`, `.pnpm-store`, `**/*.spec.ts`, `**/testUtils**`, `automation/**`, `**/e2e/**`, `**/e2e-tests/**`, `**/*.e2e.*`, `**/wdio.conf.*`, `**/wdio.*.conf.*`, `**/playwright.config.*`, `**/{astro,babel,commitlint,docusaurus,esbuild,eslint,jest,oxlint,postcss,prettier,rolldown,rollup,stylelint,svelte,tailwind,tsdown,tsup,uno,webpack}.config.*`, `**/{eslint,jest}.*.config.*`, `**/jest.setup.*`, `**/.{babelrc,eslintrc,mocharc,prettierrc}.*`.
  Script: `eslint --config configs/eslint.scanner.config.mjs .`. Read its output as a preview, not a verdict.
- [ ] **2a. The directory's own preview** (L46, L47, L52). `lint:scanner` misses what newer scanner layers report and the scan's CSS lint, dependency install and build verification. As soon as the repository is on GitHub with a build, run the community directory's *Review branch* on it (it needs the directory's GitHub App on the repository; see *Manage your plugin or theme* in the developer docs) and fix every finding; repeat before each release. Expect: no tracked agent tooling with JavaScript or CSS (`.gitignore`, Task 00), no `engine-strict`, no `createElement` outside `tests/`, the harness under `tests/`.
- [ ] **3. `nightly-mutation.yml`**: `schedule` with two crons, `"17 2 * * 1-6"` (incremental) and `"17 2 * * 0"` (every mutant, once a week), and `workflow_dispatch` with a boolean input `full`; `permissions: contents: read`. Each mutation job gets `timeout-minutes` sized for a **full** run (120 here, for `mutation` and `mutation-edge`; `report-failure` 5), not for an incremental one: the lockfile is part of the cache key, so the first run after a version bump or any dependency update tests every mutant (L39; a 45-minute limit cut the first such run off without a report). Job `mutation`: checkout without persisted credentials, `npm ci`, restore `reports/stryker-incremental.json` with `actions/cache/restore` (key: a hash of everything the results depend on that Stryker's incremental mode does not track, plus `github.run_id`; `restore-keys`: the same hash without the run id, because a cache entry never changes and each run saves under its own key). Stryker tracks the mutated sources and the test files only, so the hash, computed by a step from `hashFiles`, covers the Stryker config, the Vitest config it points at and the shared Vitest config that imports, the tsconfigs of the type checker, `tests/support/**` (the Obsidian double and the fixtures the gated tests import) and the lockfile: a change to any of them makes the next run test every mutant instead of trusting results the change may have made stale. Run `test:mutation`, or `test:mutation:full` when `full` is set or the run is the Sunday schedule (`github.event.schedule == '17 2 * * 0'`; the weekly full run also re-tests the survivors against tests written since, L14), save the incremental file with `actions/cache/save` when not cancelled (also after a failed threshold: the next run builds on it), upload `reports/mutation/`. Job `mutation-edge`: the same scheme with its own key and file and its own hash (its Stryker and Vitest configs, the shared Vite config its dom tests go through with the scripts that config imports, the tsconfigs, `tests/support/**` and the lockfile), `npm run test:mutation:edge -- $FORCE` (`--force` when `full` or on Sunday), upload `reports/mutation-edge/`. Job `report-failure` (`needs` both, `if: ${{ always() && (contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')) }}`, because a job cut off by its time limit ends as `cancelled`, which `failure()` does not see; a run a person cancels reports too; `permissions: issues: write` only): opens the issue "Nightly mutation run failed" or comments on the open one, with a link to the run (`gh issue list --search`, `gh issue comment` or `gh issue create`). The wider cache key and the Sunday full run are an Untested proposal (see the note after step 4).
- [ ] **4. `release.yml`** (`name: Release`): two triggers: `workflow_dispatch` with a required string input `version`, and tags `[0-9]+.[0-9]+.[0-9]+` (no `v`). The start by hand is the way for an agent, whose session usually cannot push tags (L38): the workflow then creates the tag itself. Workflow `permissions: contents: read`; `concurrency` group `release` without cancelling. Two jobs, so the job with write permissions never runs repository code (L32):
  - `build` (read-only token, `timeout-minutes: 45`, job output `tag`), in this order: checkout with `fetch-depth: 0` and `persist-credentials: false`; `actions/setup-node` (the checks below are plain scripts that need no install); a step **resolves the version** with `node scripts/release-version.mjs` (Task 20 step 6; the input is read only from `env:`, never pasted as `${{ inputs.version }}` into a script); then **fail unless the commit is an ancestor of `origin/main`** (`git merge-base --is-ancestor HEAD origin/main`, with an `::error` naming the version); then `node scripts/check-versions.mjs --tag "$TAG"` **before the install**, so a wrong version stops the run in seconds and not after the 20 to 30 minutes of gate and e2e; `npm ci` (install scripts run only here); `npm run verify` (it includes `check:notices`); `npm run release:package -- --tag "$TAG"` **right after the gate**, then a step that writes the sha256 of the three plugin files and the notices file to `$RUNNER_TEMP` (`sha256sum`); only then the e2e steps of `ci.yml` (display, cache restore, completeness check and save), which rebuild `dist/` and start cached Obsidian and chromedriver binaries, so what they leave must not become the release; after them `sha256sum --check --strict` of the staged files against those hashes (the job fails when a file changed meanwhile, and the plan does not rely on two builds giving the same bytes); upload `release/` as `release-files` (`if-no-files-found: error`); upload `reports/e2e/` on failure.
  - `release` (`needs: build`; `timeout-minutes: 10`; `permissions: contents: write, id-token: write, attestations: write`; **no checkout, no npm**): download `release-files`; `actions/attest` with `subject-path` over the three plugin files and `release/THIRD-PARTY-NOTICES.txt`; `gh release create "$TAG"` (`TAG` from `needs.build.outputs.tag`) with `--title "$TAG" --generate-notes`, the four files, with `--verify-tag` when a tag started the run and with `--target "$SHA"` (`github.sha`) when it was started by hand, after `gh api "repos/$GH_REPO/git/ref/tags/$TAG"` showed that the tag does not exist (with an existing tag `gh` ignores `--target`). **Only an HTTP 404 means "no such tag"**: `if lookup=$(gh api … 2>&1)` succeeding is the error "tag exists", a failure whose text lacks `HTTP 404` (a 5xx, a rate limit, the network) is a second error "could not tell", and neither goes on to `--target`; a tag the release creates with the workflow token starts no second run; and `--prerelease` while the major version is 0 (`if [ "${TAG%%.*}" = "0" ]`), so a 0.x release reaches BRAT testers without being "Latest".
  The release job's steps cannot call a script (no checkout); they are the only logic in YAML besides the ancestor check and the hashes of the build job and the failure issue. **Untested proposal:** the order of the build job (versions checked before the install, files staged and hashed right after the gate, hashes checked after the e2e run), the 404-only tag lookup, the nightly cache keys and the Sunday full run were written after the first release and have not run on GitHub; the scripts they call are unit-tested, the YAML is checked by reading and `actionlint`. If one fails on its first run, fix it on a branch and start the run again (see the end of this task).
- [ ] **5. `dependabot.yml`**: `npm` weekly, `open-pull-requests-limit: 3`, `commit-message.prefix: build`, `ignore` the majors ADR 0001 holds back (`typescript`, `eslint`, `@eslint/js` with `update-types: ["version-update:semver-major"]`, each with its blocker as a comment), `cooldown.default-days: 7` (security updates ignore it), `groups`: `wdio` (`patterns: ["@wdio/*"]`, every update type: they are released together; first, because a dependency joins the first group it matches), `dev-tooling` (development, minor and patch), `runtime` (production, minor and patch); each other major comes alone. `github-actions` weekly, `open-pull-requests-limit: 2`, `prefix: ci`, `cooldown.default-days: 7` (the semver-specific cooldown keys exist for npm only), one group for minor and patch. Dependabot rewrites the SHA and the tag comment together and does not touch `overrides`.
- [ ] **6. `pull_request_template.md`**: what changes and why; checks (`npm run verify` locally, tests written first and seen to fail, new expected failures with a text, new Nuxt UI components in `app.css`, new icons in `SHELL_ICONS`, the new-view checklist); the manual check done or "not needed" with the reason. A field for the issue a pull request closes comes once the repository has decided its issue tracker; until then leave it out.
- [ ] **7. `docs/engineering/github-setup.md`**: the workflows table (file, trigger, what it does); a section on the e2e display and the Obsidian cache (no window manager and what to watch for, how to put one back, how many cache entries are kept, why a failed run keeps its download); that `release.yml` and `nightly-mutation.yml` can only run on the Actions runner and were checked with `actionlint` only until their first run (L33; expect fixes on the first tag and the first night); the update rules: the gate decides a minor or patch; a major gets a look at its changelog and ADR 0001 first; remove an override by hand when upstream no longer needs it; never merge a workflow pin without its tag comment; an action update may be merged after reading its changes between the two tags against the inputs these workflows use, checking the new SHA with `git ls-remote`, and a green CI (say what in `release.yml` and `nightly-mutation.yml` depends on it, since they do not run on a pull request); a Dependabot change that adds or removes a bundled package turns `check:notices` red: push one commit with the regenerated file (`npm run notices`), name each new package's licence; and the **steps for the human** below.
- [ ] **8. `docs/engineering/releasing.md`**: the bump on a branch from an up-to-date `main` (`npm version <x.y.z> --no-git-tag-version`; the hook bumps and stages `manifest.json` and `versions.json`), committed as `chore: release <x.y.z>` and merged through a pull request; then, with CI green on `main`, the release is started: by hand on `main` with the input `version` (browser, `gh workflow run release.yml --ref main -f version=<x.y.z>`, or an agent's GitHub tools), or with `git tag <x.y.z> origin/main && git push origin <x.y.z>`; either publishes, so it happens only when the owner asked for the release (where direct pushes to `main` are allowed, `npm version <x.y.z>` and `git push --follow-tags` bump and tag in one step); what each release job does, how a failed run is handled (a failure before the last step leaves nothing behind, because the tag is created last with the release: fix on `main` and start again with the same version; a run started by a tag leaves the tag without a release: fix on `main`, delete the tag locally and on GitHub, start again; **a failure in the last step** can leave a draft release, because `gh release create` makes a draft, uploads the assets and publishes in separate API calls, and the tag of a start by hand is created at the publish: the draft and the attestations the run already made (signed statements about those exact files, harmless) stay, and the workflow does not delete the draft on purpose, since a step that deletes a release after a failure must be sure it is this run's draft and a wrong condition would remove a published release, which cannot be undone; look at the Releases page before starting again and delete a draft of that version by hand, or a second run makes a second draft), installing by hand, local staging (`npm run build && npm run release:package`), the notices, build provenance: `gh attestation verify main.js --repo <owner>/<repo> --signer-workflow <owner>/<repo>/.github/workflows/release.yml --source-ref refs/heads/main` (`--source-ref refs/tags/<x.y.z>` for a start by tag); `--repo` alone accepts an attestation made by any workflow on any branch or tag of the repository, so a changed `release.yml` run on a feature branch would pass it, while the pair pins the workflow and the ref; the attested bytes are the released ones because both steps read the one artifact (untested proposal: the flags are those of `gh attestation verify --help`, and the command was not run against a real release), and **beta testing with BRAT**: Obsidian has no beta channel; a tester installs BRAT, chooses *Add beta plugin* and enters the repository URL; a bare semver tag and the three assets are all BRAT needs; 0.x releases are pre-releases; from 1.0.0 on releases are normal.

## Steps for the human (report as `not-run`)

1. *Settings → Actions → General*: allow actions; the default read-only token is enough (`release.yml` asks for its permissions itself). Artifact attestations need a public repository, or GitHub Enterprise Cloud for a private one.
2. *Settings → Rules → Rulesets*, a branch ruleset for `main`: require a pull request with at least one approval; require the status check `CI / verify` (it appears after the first run); add `CI / e2e` once it has run about two weeks without a flake; block force pushes; allow only squash merges.
3. Prove the rule: a pull request with a planted type error (`const x: number = "a";` in a domain file) fails `verify` and cannot be merged; close it.
4. The first release is the first run of `release.yml` (start it by hand on `main` with the version): watch it; then start `nightly-mutation.yml` by hand once and confirm that the second run restores the first run's cache.

## Done when

`npx actionlint` (if available) reports nothing for the three workflows, or the report says it was not run; `npm run verify` exits 0. Commit `ci: workflows, dependabot and release documentation`.

Validated in the project this plan was drawn from: `ci.yml` on pull requests and on `main` (`e2e` without a window manager), `release.yml` started by hand (both jobs, the four assets as a pre-release, the attestation), and `nightly-mutation.yml` on schedule and by hand, each in the form before the changes marked *Untested proposal* in steps 3 and 4. Untested proposal: the release started by a pushed tag, a nightly run that restores the previous run's results, the failure issue itself, and a Dependabot run with cooldown and groups (checked with `actionlint` only, L33). If the first run of one fails, fix the workflow on a branch, merge it, and start the run again; a release started by hand that fails before its last step leaves no tag behind, so the same version can be used again.
