# Task 10 · Navigation, view state, settings screen

Phase A. Needs: Task 09.

**Goal.** One registered view type; each open view has its own Vue app and its own typed route, which Obsidian saves in the workspace layout; the plugin tab is fixed and keeps its own history; the shell owns a settings screen whose sections the modules contribute through their screens manifest.

## Files

Create: `src/application/shell/{routes,history}.ts`, `src/application/routes.ts` (`SETTINGS_SECTIONS`, `SettingsSection`, `Route`, `appRoutes`), `src/presentation/shell/{routing,navigation,screens}.ts`, `src/presentation/shell/components/{AppFrame,RouteOutlet,SettingsScreen}.vue`, `src/presentation/app-surface.ts`, `src/infrastructure/obsidian/shell/open-route.ts`; replace the bare view in `src/infrastructure/obsidian/shell/shell-view.ts`. The tracer's skeleton: `src/application/items/{index,module,routes}.ts`, `src/application/items/i18n/{catalog,<language>}.ts`, `src/presentation/items/{index,screens}.ts`, `src/presentation/items/components/ItemSettings.vue` (Task 18 fills them). Tests: `tests/unit/application/shell/{routes,history}.test.ts`, `tests/unit/application/routes.test.ts`, `tests/dom/presentation/shell/{navigation,settings-screen}.test.ts`, `tests/dom/infrastructure/shell/{shell-view,view-state,settings-state,open-route}.test.ts`, `tests/support/surface.ts`.

## Steps

- [ ] **1. Routes are data** (`src/application/shell/routes.ts`): `RouteLike = { readonly name: string }`; `routesOf(schema, start)` gives `{ start, decode, equals }`, where `decode` never throws (an unknown name, a missing or broken parameter, or no object at all gives `start`) and `equals` compares by value (`Schema.toEquivalence`). `SETTINGS = "settings"`; `settingsRoute(sections)` = `Schema.Struct({ name: Schema.Literal(SETTINGS), section: Schema.Literals(sections) })`. No router library: a `switch` over route names, which typecheck checks, covers a handful of screens. No placeholder screens: a route exists only when its screen does.
- [ ] **2. The history** (`src/application/shell/history.ts`, plain data): `RouteHistory` with `historyAt`, `visit`, `stepBack`, `stepForward`; a visit pushes the current route onto the back stack and clears the forward stack; a visit to the current route pushes nothing; at most `HISTORY_LIMIT = 50` steps back. Test: `history.test.ts`.
- [ ] **3. Sections in the manifest.** Add `routes` and `sections: { id, order }[]` to `ModuleManifest`, and `sectionsOf` (ordered by `order`), `SectionOf`, `routeSchemasOf`, `RouteOf` to `src/application/module.ts`. `src/application/routes.ts`: `SETTINGS_SECTIONS = sectionsOf(APP_MODULES)`, `Route = Schema.Union([settingsRoute(SETTINGS_SECTIONS), ...routeSchemasOf(APP_MODULES)])`, `appRoutes = routesOf(Route, <start>)`. The settings route needs at least one section, and the source repository's first section came with its tracer; here create the tracer module's skeleton now: `ITEMS_SECTION = "items"` in `src/application/items/routes.ts`, a manifest `defineModule({ name: "items", catalog, sections: [{ id: ITEMS_SECTION, order: 100 }] })` in `APP_MODULES`, the start route `{ name: "settings", section: "items" }`, and a section component that shows the tracer's empty state from its catalog (design intention; Task 18 replaces it with the real list). Task 17 adds the notes module's data issues with `order: 900`. Test: `tests/unit/application/routes.test.ts` pins `SETTINGS_SECTIONS` (a new section changes what the user sees, so this test changes with it).
- [ ] **4. Screens manifest** (`src/presentation/shell/routing.ts`, Vue-free, Vue only as types): `ScreenLoader = () => Promise<Component>`; `SettingsSectionPart = { label(catalog), component: ScreenLoader, badge?: ScreenLoader }`; `MenuEntry` (label from the catalog, icon, route); `ModuleScreens<Name>` = `{ screens, sections, menu?, context? }`, typed by the module's manifest so a route without a screen, a section without a part or a part for an unknown id fails typecheck in the module (`RouteNameOf`, `SectionIdOf` in `src/application/routes.ts`); `SurfaceDefinition<R>` = `Routes<R>` plus `screen(route)`, `menu`, `context?`, `sections`; `frameMenu(definition)` adds the shell's settings entry after the modules' entries whenever there is a section, opening the first section of `sections`; `ViewNavigation` (`current`, `history`, `navigate`, `back`, `forward`, `onChange`) and `memoryNavigation(definition)` with `reset(route)`, recording the routes it visited. `src/presentation/shell/screens.ts`: `{ screens: { settings: () => import("./index").then(m => m.SettingsScreen) }, sections: {} } satisfies ModuleScreens<"shell">`. Every module's `screens.ts` loads components only through `import()` (global constraint 5).
- [ ] **5. The composition** (`src/presentation/app-surface.ts`): `MODULE_SCREENS: { readonly [Name in AppModuleName]: ModuleScreens<Name> }`, the **second shared line** a module adds (L3); a module of `APP_MODULES` without its entry does not compile. `appSurface` merges the screens, orders the section parts by `SETTINGS_SECTIONS`, joins the modules' menu entries in module order and takes the one context area. It holds no rule of its own. Update `tests/unit/application/modules.test.ts` to require `src/presentation/<name>/screens.ts` for each module.
- [ ] **6. Vue side** (`navigation.ts`): `provideRouting`, `useRoute()`, `useNavigate()`, `useHistory()` (`canGoBack`, `canGoForward`, `back`, `forward`). `RouteOutlet.vue` loads the route's screen lazily, shows `NotFoundState` when `screen` returns `undefined`, and keys the screen by route **name**, so a screen with sections stays mounted across them. `AppFrame.vue`: a labelled `<nav>` with back and forward icon buttons (shown once the history has a step; `aria-disabled` when there is nowhere to go), the context slot, one button per menu entry with `aria-current="page"` on the current one (compared by route name, so "Settings" is current on every section); a labelled `<section>` with the outlet; a size container that lays the navigation out as a sidebar from 860 px of its own width and as a row below (window width plays no part; an Obsidian pane can be narrow on a desktop). Set `lang` to the UI language on the frame.
- [ ] **7. `SettingsScreen.vue`**: a labelled `<nav>` (`aria-label` from the shell catalog) with one button per section, `aria-current="page"` and a bar on the current one, each in the tab order, in a row that wraps at 320 px; below it the current section; with a single section no navigation; a section id without a part shows not-found; the chosen entry keeps the focus while the section remounts. A part's `badge` loads lazily beside its label (L10).
- [ ] **8. `ShellView`** (`shell-view.ts`), constructed with `(leaf, runtime, surfaces, definition, loadSurface = importSurface)`:
  - `navigation = false` (L23): with `true`, Obsidian records leaf history but a plain click in the file explorer (`getLeaf(false).openFile`) opens the note in the plugin's tab and the view vanishes;
  - `getViewType()` = `SHELL_VIEW_TYPE`, `getDisplayText()` = `PRODUCT_NAME`, `getIcon()` an Obsidian icon name;
  - `getState()` = `{ ...super.getState(), route }`; `setState(state)` decodes the route: the **first** state Obsidian sets (a restored layout, `openRoute` on a new view) is `reset` and starts the history, a later one is a navigation; every route change calls `app.workspace.requestSaveLayout()`;
  - `onOpen`: register the close in `surfaces` **before** `await loadSurface()` (a view closed while the module loads never mounts), `contentEl.empty()`, then `mountSurface(contentEl, runtime, { surface, navigation })`. Obsidian calls `onOpen` before `setState`, so a restored view mounts on the start route and switches in the same task, before the next paint;
  - `onClose`: remove from `surfaces` and close.
- [ ] **9. Opening from outside** (`openRoute(workspace, route?)`, `open-route.ts`): takes the first leaf of `SHELL_VIEW_TYPE`, else `workspace.getLeaf(true)`; calls `setViewState({ type, active: true, state: { route } })` on a new leaf or when a route is given; then `revealLeaf`. Without a route an open view keeps its own. The `open-view` command and the ribbon use it; a feature command passes its route.
- [ ] **10. Tests.** `tests/support/surface.ts`: `testSurface()` is a definition with test-only routes (two screens, an item with a parameter, a route without a screen), `mountTest` mounts it, `mountApp(root, runtime, options)` mounts the real `appSurface`; navigation is proved on test routes so the plugin ships no fake screens. `navigation.test.ts` (navigate, back, forward, limit, not-found), `settings-screen.test.ts` (two sections, focus kept across sections, one section without navigation, an unknown section), `view-state.test.ts` (restore, a broken state falls back to the start, two views keep their own routes), `settings-state.test.ts` (a restored state on each section), `open-route.test.ts`, `shell-view.test.ts` (mounts once, a view closed while loading never mounts, plugin unload closes the surface before the runtime is disposed).
