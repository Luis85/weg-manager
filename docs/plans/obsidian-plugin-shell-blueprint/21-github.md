# Task 21 · GitHub workflows and dependency updates

Phase D. Needs: Task 20.

**Goal.** CI runs the same gate as the developer's machine; e2e runs in real Obsidian beside it; mutation runs nightly; a release is built read-only from a tag on `main` and published by a job that runs no repository code. All logic stays in npm scripts; the YAML only installs Node and calls them. The agent writes the files; the human enables them (steps at the end).

## Files

Create: `.github/workflows/ci.yml`, `.github/workflows/nightly-mutation.yml`, `.github/workflows/release.yml`, `.github/dependabot.yml`, `.github/pull_request_template.md`, `configs/eslint.scanner.config.mjs`, `docs/engineering/github-setup.md`, `docs/engineering/releasing.md`. Modify: `package.json` (script `lint:scanner`).

## Action pins

Pin every action by its full commit SHA with the tag as a comment (`uses: actions/checkout@<sha> # v7.0.1`); a tag can be moved, a SHA cannot; never write `@v7`. The source repository pins, on 2026-11-22: `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`, `actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0`, `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2`, `actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2`, `actions/cache@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0` (also `actions/cache/restore` and `actions/cache/save` at the same SHA), `actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2`. Re-resolve each with `git ls-remote https://github.com/<owner>/<action> refs/tags/<tag>` and use the newest release whose inputs these workflows use unchanged.

## Steps

- [ ] **1. `ci.yml`**: on push to `main` and every pull request; `permissions: contents: read`; `concurrency` group per ref with `cancel-in-progress` only for pull requests (two merges to `main` in a row must each finish). Jobs, each `runs-on: ubuntu-latest` with a `timeout-minutes`, each `actions/checkout`, `actions/setup-node` with `node-version-file: .nvmrc` and `cache: npm`, `npm ci`:
  - `verify`: `npm run verify`; upload `reports/junit.xml` and `reports/coverage/cobertura-coverage.xml` as `reports` when not cancelled, and `dist/` as `plugin`.
  - `e2e`: resolve the Obsidian versions for the cache key (`node tests/e2e/wdio.conf.mts | grep 'obsidian-cache-key:' > obsidian-versions-lock.txt`, then `rm -rf .obsidian-cache`), `actions/cache` on `.obsidian-cache` keyed `obsidian-cache-${{ runner.os }}-${{ hashFiles('obsidian-versions-lock.txt') }}`, start Xvfb with a window manager (`sudo apt-get install -q -y herbstluftwm`, `Xvfb :99 -screen 0 1280x1024x24 +extension GLX -noreset &`, `DISPLAY=:99` into `$GITHUB_ENV`), `npm run test:e2e` with `WDIO_MAX_INSTANCES: 2`, upload `reports/e2e/` on failure. The download stays in the Actions cache, never in an artifact (Obsidian's terms forbid redistribution).
  - `scanner-lint`: `npm run lint:scanner` with `continue-on-error: true` on the step and a `::warning` annotation when it failed: it approximates the community directory's source scan and never blocks.
- [ ] **2. `lint:scanner`** (`configs/eslint.scanner.config.mjs`): only `eslint-plugin-obsidianmd`'s `recommended` config with the scanner's rule changes and fixed ignore list from the plugin's documented scanner configuration; files git does not track are skipped (the scanner sees a clone); `.js` files without type information. Script: `eslint --config configs/eslint.scanner.config.mjs .`. Read its output as a preview, not a verdict.
- [ ] **3. `nightly-mutation.yml`**: `schedule` (`cron: "17 2 * * *"`) and `workflow_dispatch` with a boolean input `full`; `permissions: contents: read`. Job `mutation`: checkout without persisted credentials, `npm ci`, restore `reports/stryker-incremental.json` with `actions/cache/restore` (key: Stryker config + its Vitest config + lockfile + `github.run_id`; `restore-keys`: the same without the run id, because a cache entry never changes and each run saves under its own key), run `test:mutation` or `test:mutation:full` when `full` is set, save the incremental file with `actions/cache/save` when not cancelled (also after a failed threshold: the next run builds on it), upload `reports/mutation/`. Job `mutation-edge`: the same scheme with its own key and file, `npm run test:mutation:edge -- $FORCE` (`--force` when `full`), upload `reports/mutation-edge/`. Job `report-failure` (`needs` both, `if: failure()`, `permissions: issues: write` only): opens the issue "Nightly mutation run failed" or comments on the open one, with a link to the run (`gh issue list --search`, `gh issue comment` or `gh issue create`).
- [ ] **4. `release.yml`**: two triggers: `workflow_dispatch` with a required string input `version`, and tags `[0-9]+.[0-9]+.[0-9]+` (no `v`). The start by hand is the way for an agent, whose session usually cannot push tags (L38): the workflow then creates the tag itself. Workflow `permissions: contents: read`; `concurrency` group `release` without cancelling. Two jobs, so the job with write permissions never runs repository code (L32):
  - `build` (read-only token, job output `tag`): checkout with `fetch-depth: 0` and `persist-credentials: false`; a step **resolves the version**: started by hand it fails unless `github.ref` is `refs/heads/main` and takes the input, started by a tag it takes `github.ref_name`; it fails unless the version matches `^[0-9]+\.[0-9]+\.[0-9]+$` as one string (bash `[[ =~ ]]`, so an input with a line break cannot pass), and, started by hand, when `git rev-parse -q --verify "refs/tags/<version>"` finds the tag. Read the input only from `env:`, never paste `${{ inputs.version }}` into a script. Then **fail unless the commit is an ancestor of `origin/main`** (`git merge-base --is-ancestor HEAD origin/main`, with an `::error` naming the version); `npm ci` (install scripts run only here); `npm run verify` (it includes `check:notices`); the e2e setup of `ci.yml` and `npm run test:e2e`; `npm run release:package -- --tag "$TAG"`; upload `release/` as `release-files` (`if-no-files-found: error`); upload `reports/e2e/` on failure.
  - `release` (`needs: build`; `permissions: contents: write, id-token: write, attestations: write`; **no checkout, no npm**): download `release-files`; `actions/attest` with `subject-path` over the three plugin files and `release/THIRD-PARTY-NOTICES.txt`; `gh release create "$TAG"` (`TAG` from `needs.build.outputs.tag`) with `--title "$TAG" --generate-notes`, the four files, with `--verify-tag` when a tag started the run and with `--target "$SHA"` (`github.sha`) when it was started by hand, after `gh api "repos/$GH_REPO/git/ref/tags/$TAG"` showed that the tag does not exist (with an existing tag `gh` ignores `--target`); a tag the release creates with the workflow token starts no second run; and `--prerelease` while the major version is 0 (`if [ "${TAG%%.*}" = "0" ]`), so a 0.x release reaches BRAT testers without being "Latest".
  The release job's steps cannot call a script (no checkout); they are the only logic in YAML besides the failure issue.
- [ ] **5. `dependabot.yml`**: `npm` weekly, `open-pull-requests-limit: 3`, `commit-message.prefix: build`, `ignore` the majors ADR 0001 holds back (`typescript`, `eslint`, `@eslint/js` with `update-types: ["version-update:semver-major"]`, each with its blocker as a comment), `cooldown.default-days: 7` (security updates ignore it), `groups`: `wdio` (`patterns: ["@wdio/*"]`, every update type: they are released together; first, because a dependency joins the first group it matches), `dev-tooling` (development, minor and patch), `runtime` (production, minor and patch); each other major comes alone. `github-actions` weekly, `open-pull-requests-limit: 2`, `prefix: ci`, `cooldown.default-days: 7` (the semver-specific cooldown keys exist for npm only), one group for minor and patch. Dependabot rewrites the SHA and the tag comment together and does not touch `overrides`.
- [ ] **6. `pull_request_template.md`**: what changes and why; the backlog item; checks (`npm run verify` locally, tests written first and seen to fail, new expected failures with a text, new Nuxt UI components in `app.css`, new icons in `SHELL_ICONS`, the new-view checklist); the manual check done or "not needed" with the reason.
- [ ] **7. `docs/engineering/github-setup.md`**: the workflows table (file, trigger, what it does); that `release.yml` and `nightly-mutation.yml` can only run on the Actions runner and were checked with `actionlint` only until their first run (L33; expect fixes on the first tag and the first night); the update rules: the gate decides a minor or patch; a major gets a look at its changelog and ADR 0001 first; remove an override by hand when upstream no longer needs it; never merge a workflow pin without its tag comment; an action update may be merged after reading its changes between the two tags against the inputs these workflows use, checking the new SHA with `git ls-remote`, and a green CI (say what in `release.yml` and `nightly-mutation.yml` depends on it, since they do not run on a pull request); a Dependabot change that adds or removes a bundled package turns `check:notices` red: push one commit with the regenerated file (`npm run notices`), name each new package's licence; and the **steps for the human** below.
- [ ] **8. `docs/engineering/releasing.md`**: the bump on a branch from an up-to-date `main` (`npm version <x.y.z> --no-git-tag-version`; the hook bumps and stages `manifest.json` and `versions.json`), committed as `chore: release <x.y.z>` and merged through a pull request; then, with CI green on `main`, the release is started: by hand on `main` with the input `version` (browser, `gh workflow run release.yml --ref main -f version=<x.y.z>`, or an agent's GitHub tools), or with `git tag <x.y.z> origin/main && git push origin <x.y.z>`; either publishes, so it happens only when the owner asked for the release (where direct pushes to `main` are allowed, `npm version <x.y.z>` and `git push --follow-tags` bump and tag in one step); what each release job does, how a failed run is handled (a run started by hand leaves nothing behind, because the tag is created last with the release: fix on `main` and start again with the same version; a run started by a tag leaves the tag without a release: fix on `main`, delete the tag locally and on GitHub, start again), installing by hand, local staging (`npm run build && npm run release:package`), the notices, build provenance (`gh attestation verify main.js --repo <owner>/<repo>`; the attested bytes are the released ones because both steps read the one artifact), and **beta testing with BRAT**: Obsidian has no beta channel; a tester installs BRAT, chooses *Add beta plugin* and enters the repository URL; a bare semver tag and the three assets are all BRAT needs; 0.x releases are pre-releases; from 1.0.0 on releases are normal.

## Steps for the human (report as `not-run`)

1. *Settings → Actions → General*: allow actions; the default read-only token is enough (`release.yml` asks for its permissions itself). Artifact attestations need a public repository, or GitHub Enterprise Cloud for a private one.
2. *Settings → Rules → Rulesets*, a branch ruleset for `main`: require a pull request with at least one approval; require the status check `CI / verify` (it appears after the first run); add `CI / e2e` once it has run about two weeks without a flake; block force pushes; allow only squash merges.
3. Prove the rule: a pull request with a planted type error (`const x: number = "a";` in a domain file) fails `verify` and cannot be merged; close it.
4. The first release is the first run of `release.yml` (start it by hand on `main` with the version): watch it; then start `nightly-mutation.yml` by hand once and confirm that the second run restores the first run's cache.

## Done when

`npx actionlint` (if available) reports nothing for the three workflows, or the report says it was not run; `npm run verify` exits 0. Commit `ci: workflows, dependabot and release documentation`.

**Proven in the source repository:** `CI / verify`, `CI / e2e` and `CI / scanner-lint` on every pull request. **Never run there:** `release.yml`, `nightly-mutation.yml`, and a Dependabot run with cooldown and groups (PBI-67).
