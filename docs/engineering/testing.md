# Testing

Tests come first. Each behaviour step writes the failing test, sees it fail, then implements. A "discriminating check" counts only once it has been seen to fail on a planted defect. `npm run verify` runs the unit and dom projects with coverage; the end-to-end suite and mutation testing run on their own (see the end-to-end section).

## Projects

| Project | Files | Environment | Use for |
| --- | --- | --- | --- |
| `unit` | `tests/unit/**/*.test.ts` | node | domain, application, scripts, harness layers, logging |
| `dom` | `tests/dom/**/*.test.ts` | happy-dom + Vue/Nuxt UI plugins | lifecycle, settings tab, views, components |
| e2e | `tests/e2e/specs/*.e2e.ts` | real Obsidian (WebdriverIO) | see [End-to-end tests](#end-to-end-tests-in-obsidian) |

Tests mirror the module folders: `tests/<project>/<layer>/<module>/`, e.g. `tests/unit/application/shell/` for `src/application/shell/`. Tests of the composition (plugin load through `main.ts`, `bootstrap.ts`, the files at a layer root) stay above them, e.g. `tests/dom/lifecycle.test.ts`.

- Run one file: `npx vitest run tests/dom/presentation/communities/screen.test.ts`
- Run one project: `npx vitest run --project unit`
- Run tests by name: `npx vitest run -t "read-only"`

Coverage (`npm run test:coverage`) applies to `src/**` and enforces lines 90, statements 90, functions 90 and branches 85.

## Support code

- `tests/support/obsidian/` is an in-memory double of the `obsidian` API. `getLanguage()` returns German (`DEFAULT_TEST_LANGUAGE`), the product's primary language, so the exact German texts of the dom tests stay meaningful; a suite that calls `setLanguage("en")` sets it back to `DEFAULT_TEST_LANGUAGE` in `afterEach` (see `tests/dom/language.test.ts`). `vault`, `metadataCache` and `workspace` are `Events`: `trigger(name, ...args)` fires an event and `listenerCount(name?)` counts live listeners. `workspace.layoutReady = false` with `markLayoutReady()` simulates startup (see the metadata cache below for the cache's side). `TFile` and `TFolder` are classes, so `instanceof` works. A suite opts in with `vi.mock("obsidian", () => import("@test/obsidian"))`. Without that, importing `obsidian` throws `OBSIDIAN_REQUIRES_TEST_DOUBLE`.
  - Views have `getState`/`setState`, `navigation` (false by default, as `ShellView` sets it) and `app`. `leaf.setViewState` behaves as in Obsidian 1.15.1: a new view type opens the view, then the view gets the state; an open view of the same type is kept and only gets the new state. `workspace.layoutSaves` counts `requestSaveLayout` calls.
  - `app.loadLocalStorage`/`saveLocalStorage` store JSON like Obsidian (a falsy value clears the key; a broken entry reads as `null`); `app.localStorage.setRaw` plants a raw entry.
- **The double's vault** (`vault.ts`, `metadata-cache.ts`, `file-manager.ts`) behaves as Obsidian 1.15.1 does, and `tests/e2e/specs/note-store.e2e.ts` checks that against the real app:
  - `vault`: `getFileByPath`, `getFolderByPath`, `getAbstractFileByPath`, `getMarkdownFiles`, `read` and `cachedRead` (without a leading BOM, as Obsidian decodes), `create` (refuses a taken path and a missing folder), `createFolder` (creates parents, one `create` each), `process` (hands the callback the raw text, BOM and CRLF included; writes and fires `modify` only when the text changes; what the callback throws rejects unchanged; a file deleted meanwhile rejects with ENOENT without calling back). The adapter's updates go through `process`. Each write waits a macrotask first, as disk I/O does, and refuses a path that `normalizePath` would change.
  - `metadataCache.getFileCache`: indexes a write a macrotask later and then fires `changed`, `resolve` and `resolved`; `null` before a new file is indexed, the old metadata before a changed one is. Broken YAML has no `frontmatter`. The block is found as the cache finds it: past one BOM, LF or CRLF, closed by the first line that starts with `---`. A frontmatter block is a `sections` entry of type `yaml`, also when it cannot be read; the double models no other section. `await metadataCache.whenIndexed()` waits until every pending file is indexed.
  - **Startup**, as `tests/e2e/specs/vault-ready.e2e.ts` measured it. By default every file is indexed already, as after a warm restart or for a plugin enabled in a running app (`vault.setMarkdownFileCount` indexes its notes at once, without events). `metadataCache.startCold()` is a vault Obsidian has never indexed: every Markdown file loses its metadata and is indexed again in vault order, one per macrotask, each with `changed`, `resolve` and `resolved`, so `resolved` fires while others still wait, as in Obsidian. `metadataCache.resolveAll()` is what a warm restart fires after the layout is ready: `resolve` per file, then one `resolved`. There is no "resolved" flag, because Obsidian has none; completeness shows only through `getFileCache`. Combine them with `layoutReady = false` and `markLayoutReady()` (see `tests/dom/infrastructure/shell/vault-ready.test.ts`).
  - `fileManager.processFrontMatter` (parses the file's text, writes only on a change, removes the block when every key is gone; no BOM, as `getFrontMatterInfo` reads; the plugin no longer calls it, the fidelity scenarios still record it), `renameFile` (keeps the `TFile`, fires `rename`), `trashFile` (`metadataCache` `deleted`, `vault` `delete`, then `metadataCache` `resolved`; resolves `true`).
  - `normalizePath`, `parseYaml`, `stringifyYaml`, `YAMLParseError`. The YAML copy handles flat maps of text, numbers, booleans, null and lists, with LF or CRLF; it rejects what records never hold (nested maps, block scalars) instead of guessing. Tests of the pure line edit and the serialiser use the real `yaml` package (a dev dependency, YAML 1.2 core as Obsidian parses, and 1.1 for older tools), not this copy; `note-write-fidelity.e2e.ts` checks the serialiser against Obsidian's own `parseYaml`.
  - `TFolder.children` and `vault.getRoot()`, kept up to date by every write.
  - Knobs: `vault.failReads`, `vault.failWrites`, `vault.holdWrites()`/`releaseWrites()`/`heldWrites()`, `vault.setMarkdownFileCount(n)`, `vault.seedFile(path, text)` for a file that appears from outside (Sync, another app; folders included, no checks, also a path in NFD).
  - `vault.caseInsensitive = true` models the disk of Windows and macOS: a write onto a path that differs from another entry only in case or Unicode form fails with EEXIST, and renaming a file to another case of its own name works. Lookups stay exact, as Obsidian's are, so a test on this disk proves the adapter finds clashes itself instead of relying on the file system. The contract runs on the double with and without it.
  - Not modelled: link updates on rename (and the `resolve` events they cause), folder renames, `vault.modify`, `vault.delete`.
- `tests/support/layers.ts` holds in-memory Layers:
  - the store, with `holdSaves`/`releaseSaves`/`heldSaves` and `setFailSave`. By default an interrupted held save never writes. `uncancellableSaves: true` models the real adapter over `plugin.saveData`: once started, the save writes even if the caller is interrupted. Use it to test interruption;
  - `controllableRead`, a use case of the plugin's shape whose value is fixed, failing (`VaultReadError`) or changed, with `hold`/`release`/`set`, for the runtime composables' tests (`testRuntime().source`);
  - recording notifier (with `hold`/`release`/`held`), logger and clipboard;
  - sequential incident ids `T-1`, `T-2`, …
  - `recordingEventBus()`: the real `EventBusLive` that records every published event, with `failNextPublish`.
- `tests/support/surface.ts` mounts surfaces: `mountApp(root, runtime, options)` mounts the app's own `appSurface` on an in-memory navigation; `testSurface()` is a definition with test-only routes (two screens, an item with a parameter, a route without a screen) and `mountTest` mounts it. Navigation is proved on these, so the plugin ships no fake screens. `memoryNavigation` (from `presentation/shell/host`) records the routes it visited.
- `sequentialIdGenerator()` (`src/infrastructure/memory/notes/`) is the `IdGenerator` for tests and the harness: UUIDs counting up from `00000000-0000-4000-8000-000000000001`, one counter per call. `testRuntime` provides one.
- `memoryNoteStore()` (`src/infrastructure/memory/notes/`) is the one in-memory `NoteStore`, for tests and the harness. It works on data, not text: byte fidelity is the Obsidian adapter's. Its handles seed and delete notes as an outside editor would (`seed(path, frontmatter | "none" | "broken", body)`, `removeOutside(path)`), look behind the port (`body`, `isFolder`) and switch failures on (`setFailReads`, `setFailWrites`, `holdWrites`/`releaseWrites`/`heldWrites`). Reads see writes at once; Obsidian's cache lags. Built where an `EventBus` is, it publishes for every write and seed the file events the host event adapter publishes for the Obsidian adapter; `tests/support/notes/store-events.ts` lists them per step, and both sides are checked against that list (`tests/unit/infrastructure/notes/memory-note-store-events.test.ts`, `tests/dom/infrastructure/notes/store-events.test.ts`). A seed before the layer is built publishes nothing.
- **NoteStore contract** (`tests/support/notes/contract.ts`): the same cases run against the in-memory adapter (`tests/unit/infrastructure/notes/memory-note-store.test.ts`) and against the Obsidian adapter on the double, once on a case-sensitive and once on a case-insensitive disk (`obsidian-note-store.test.ts`). `contract-clashes.ts` holds the clash cases (case, NFC/NFD, rename onto another note, rename to its own name in another case). A behaviour the port promises goes into the contract, not into one adapter's test: also that a throw of `change` is a defect and writes nothing, and that a note deleted while the write waits fails with `NoteNotFoundError`. The Obsidian adapter's byte fidelity (the reviewer's note with comments and number forms, a BOM, CRLF, a refused layout) is tested on the double in `obsidian-note-store.test.ts`; the pure steps in `tests/unit/domain/notes/note-text.test.ts`, `yaml-text.test.ts` and `tests/unit/application/notes/note-text.test.ts`, with fast-check properties: every written value reads back exactly, and on generated notes every byte outside the patched keys stays.
- **Fidelity scenarios** (`tests/support/notes/scenarios.ts`): `vaultFacts` calls the vault, metadata cache and file manager directly; `storeScenario` drives the `NoteStore` through the probe API (`probe-api.ts`); `readinessScenario` (`tests/support/readiness-scenario.ts`) records `changed`, `resolve`, `resolved` and `deleted` around a create, an edit and a trash. Each records results and events. `tests/unit/support/obsidian-double.test.ts` runs them on the double, the e2e specs in Obsidian, and both compare with the same expectation (`fidelity.ts`). A difference is a bug in the double: fix the double, never the expectation alone. Keep each step to what Obsidian does the same way every run: whether a new file's index or an immediate write to it comes first varies, so steps settle in between. `executeObsidian` sorts the keys of what it passes and turns `undefined` into `null`, so the scenarios return plain JSON and show key order through file texts.
- **The note index.** `tests/support/notes/index-fixture.ts` builds the index over the in-memory store on a recording bus, with in-memory settings, logger and notifier; `reads()` and `scans()` count `NoteStore.read` and `unreadable` calls, `setFailUnreadable` fails `unreadable` alone, and `countingType()` counts decodes. Its effects publish `vaultReady`, wait for a snapshot (`until`, `untilUnindexed`, `built`), record every snapshot (`recordSnapshots`) and let forked fibers run (`settle`). The unit specs run under `TestClock`, so a batch closes when the test moves the clock by `INDEX_BATCH_QUIET`, never after a real sleep: `note-index-build`, `-follow`, `-lifecycle` and `-budget.test.ts` in `tests/unit/application/notes/`. `testOther` is a second test type, so a note can change type; `throwingType` makes a decode throw, for the defect path. `tests/support/notes/reference-types.ts` declares the reference vault's `community` and `item` types, for the budget test and the probe.
- `tests/support/runtime.ts` provides `testRuntime(options)`: a full `AppRuntime` plus handles to every Layer, including `notes` (the in-memory `NoteStore`), the note index for the plugin's types (`appNoteTypes`) and any extra `noteTypes`, the community selection over an in-memory device store (`device` seeds it, `deviceStoreInMemory` from `src/infrastructure/memory/shell/`) and `source` (see above); `vaultReady()` publishes `LayoutReady` and `VaultReady`, so the first build runs. Use `rejectUpdates` to simulate a service that rejects a value the form accepted, and `language: "en"` for the English catalog (German by default). Hand-built Layers in unit tests add `testMessages` (German) from `tests/support/layers.ts`.
- **Communities.** `tests/support/communities/fixture.ts` builds the module over the index fixture (community type only), a sequential id generator and an in-memory device store that counts writes; its specs run under `TestClock`, `ready` builds the index, `indexed` lets it read one batch. `tests/support/communities/screen.ts` mounts the app on the community settings over the in-memory store (`openCommunities`) with handles to query, type, click and wait for the index (`until`), and `fill`/`save` for the form.

## Lint

`npm run lint` runs oxlint, then ESLint. oxlint owns the rules that need no type information (`.oxlintrc.json`); ESLint owns the ones that do and the plugin rules (`eslint.config.mjs`, whose oxlint block turns off what oxlint covers). Three rules are on because nothing else catches them:

- `eqeqeq` and `typescript/no-non-null-assertion` in oxlint: `==` and `!=`, and `value!`. Narrow with a check or throw a clear error instead of asserting.
- `@typescript-eslint/switch-exhaustiveness-check` in ESLint (it needs types): a `switch` over a union lists every member, so a new member breaks the build where it is not handled. A `switch` with a `default` over a union does not pass; write the cases out, or use conditions when only a few members matter (`pathsToRead` in `index-batches.ts`).

Each was proven with a planted violation before it was turned on (no finding) and after (the finding, in the tool named above). A rule that cannot be shown to fail on a plant does not belong in the config.

## Mutation testing

- `npm run test:mutation` runs incrementally; `npm run test:mutation:full` re-runs every mutant.
- Stryker mutates `src/domain` and `src/application` and runs only their unit tests, with the TypeScript checker on.
- Before pushing a change to one module, run Stryker on its files only: `npx stryker run configs/stryker.config.mjs --mutate "src/domain/communities/**/*.ts,src/application/communities/**/*.ts"`. The communities module scores 100 %; keep it there.
- Thresholds: break 75, low 80, high 90. Never lower them.
- A `// Stryker disable` comment needs its reason on the same line.
- Reports land in `reports/mutation/`. The nightly GitHub workflow runs `npm run test:mutation` against the cached `reports/stryker-incremental.json`, so only mutants whose code or tests changed run again; started by hand with `full` it re-runs every mutant. A failed night opens or updates the issue "Nightly mutation run failed".

## Browser harness

`npm run dev:ui` serves `harness/`: two surfaces on one runtime (one of them 320 px wide, so its frame shows the navigation as a row), each with its own in-memory route, a theme switch, and visible notices. `?scenario=` selects the state:

| Scenario | Shows |
| --- | --- |
| `loaded` (default) | two communities, Ahornweg 12 and its Tiefgarage; the switch asks for a choice |
| `empty` | no community: the empty state with its create action |
| `invalid` | a valid community beside a broken colour, a duplicate short code, an unreadable note in the folder and a malformed `schema` elsewhere |
| `readonly` | a note of a newer schema version beside a valid one |
| `failure` | the index's first read fails: the failure with retry, which then reads the communities |

The fake host (`harness/fake-host.css`) plays Obsidian 1.15.1's default theme: the theme variables read from the running app in light and dark, and Obsidian's base rules that reach plugin markup (button chrome, text inputs, heading sizes and margins). Take new values from the app, not from memory: print them from `getComputedStyle(document.body)` in a throwaway e2e spec. The dev server scopes the plugin CSS with the same transform as the build. Below 720 px the two surfaces stack and stretch to the window.

The note index runs in every scenario over the in-memory `NoteStore`, with the plugin's registry (`appNoteTypes`). The browser has no metadata cache to wait for, so the harness publishes `LayoutReady` and `VaultReady` once its services are built, and the index builds at once from the notes the scenario seeds.

## End-to-end tests in Obsidian

`npm run test:e2e` builds the plugin and runs `tests/e2e/specs/*.e2e.ts` with WebdriverIO and [`wdio-obsidian-service`](https://github.com/jesse-r-s-hines/wdio-obsidian-service) in a **real Obsidian app**. Background and alternatives: [Testing research](../design/research/Testing%20research%20-%20Obsidian%20end-to-end%20tests.md).

- **Versions.** The suite runs the latest Obsidian app on the latest installer (`latest/latest`); CI does the same.
  - `OBSIDIAN_VERSIONS` takes other app/installer pairs. For example, `earliest/earliest` is `minAppVersion` (1.15.1) on the oldest installer it accepts (1.5.8, Electron 28).
  - In PowerShell, set it with `$env:OBSIDIAN_VERSIONS="earliest/earliest"` first.
- **First run.** The first run downloads Obsidian into `.obsidian-cache/` (git-ignored, about 1.3 GB unpacked). Never commit or share it: Obsidian's terms forbid redistribution.
- **Display.** On Linux without a display, run `xvfb-run -a npm run test:e2e`. Windows and macOS need nothing extra.
- **Isolation.** Each spec file gets a fresh Obsidian with a copy of `tests/e2e/vaults/basic`, and `dist/` is installed as the plugin. `vault-ready.e2e.ts` switches to a fresh copy of the reference vault with `browser.reloadObsidian({ vault })`, which Obsidian has never indexed.
- **Reference vault.** `scripts/reference-vault.mjs` writes the desktop reference profile of F-21: two communities, 200 Punkte and 2,000 notes with frontmatter in total, plus 200 plain Markdown notes without it. `referenceVault({ seed, points, records, plain })` returns paths and texts; `writeReferenceVault(target, options)` replaces the folder with them. The same seed gives the same bytes: a seeded generator, no clock, no `Math.random` (`tests/unit/scripts/reference-vault.test.ts`). Records follow ADR 0007 (`schema: weg-manager.<type>/v1`, `id: <type>-<uuid>`, snake_case keys, `community_id` on everything but communities). Only `community` is specified so far, so the rest is the generic type `item` (`kind: point` or `note`); the generator follows the real types as they are built. The profile's 1,000 attachments are left out: the index reads frontmatter, never a binary. `npm run vault:reference` (part of `test:e2e`) writes it into the git-ignored `tests/e2e/vaults/reference/`; it is never committed.
- **Probe plugin.** `tests/e2e/probe-plugin/` is a second plugin for the suite only. `npm run build:probe` (part of `test:e2e`) bundles it with `configs/vite.probe.config.ts` from the real adapter source into `tests/e2e/probe-plugin/dist/` (git-ignored), and `wdio.conf.mts` installs it beside `dist/`. It exposes the Obsidian `NoteStore` as `plugins.noteStoreProbe.api`, so a spec calls the store without any hook in the plugin itself. `plugins.noteStoreProbe.events` is the note index for the reference types (`counts()`, `titleShown(path, title)`), built on the probe's own runtime before the plugin's real `hostEventsLayer`, as the plugin composes them; the recorder marks `index:ready` when its first build is published. `plugins.noteStoreProbe.startup` records from the probe's `onload` on how Obsidian got ready (layout, `create`, `changed`, `resolve`, `resolved`, with cache counts at the layout and the first `resolved`), and runs the plugin's real `hostEventsLayer` on a runtime of its own, with a count of cached notes at its `LayoutReady` and `VaultReady`.
- **Cache.** The download cache is `.obsidian-cache/` in the checkout. In a git worktree, a symlink to the main checkout's cache avoids a second download.
- **Language.** Without a stored choice Obsidian takes its language from Chromium's locale, which is `en-US` in CI and containers. `wdio.conf.mts` passes `--lang=de`, so Obsidian and the plugin start German and the specs assert German texts. `language.e2e.ts` switches to English the way Obsidian's own setting does: `localStorage` key `language`, then a plugin reload.
- **Writing specs.** `browser.executeObsidian(({ app, obsidian }, ...args) => …)` runs code inside Obsidian. The function is serialised, so pass values as arguments; closures do not work. Shared helpers live in `tests/e2e/support.ts`: console spy, open view, `data.json`, plugin reload, settings tab content, light/dark switch.
- **Gate.** `test:e2e` is not part of `verify`, because it needs a display and a download. CI runs it as a separate `e2e` job, which is not a required check yet (see [github-setup.md](github-setup.md)). The release workflow runs it too, in its read-only `build` job, and a failing e2e run stops the release. A change to lifecycle, settings tab, theme, pop-out, view state or vault behaviour needs a passing e2e run.

## Scanner-equivalent lint

`npm run lint:scanner` approximates the source scan of Obsidian's community directory. It runs `configs/eslint.scanner.config.mjs` over the repo: only `eslint-plugin-obsidianmd`'s `recommended` config, the rule changes and the fixed ignore list from the plugin's [scanner configuration](https://github.com/obsidianmd/eslint-plugin/blob/a998a5992b7bf9b6f3e0fe1e61a3ad180546f4a5/docs/configuration.md#community-plugin-scanner-configuration). Our own ignores (such as `.claude/**`) and Vue rules do not apply.

- **What it adds to the scanner's list.** Files git does not track are skipped, because the scanner sees a clone. Bundled JavaScript outside `src/` is skipped by the scanner's content rule. `.js` files are linted without type information, because no tsconfig here takes them in.
- **Not exact.** The scanner also turns most remaining errors into warnings and adds stricter layers for new submissions. Read the output as a preview, not a verdict.
- **Informational.** It is not part of `verify`. CI runs it as the `scanner-lint` job with `continue-on-error`, so findings show in the log but never block.
- **Known failure.** `.claude/skills/archify/explainer/reader.js` fails with `no-unsanitized/property` (it assigns `innerHTML`) and other errors. The owner decided to deal with it at submission time; options are in [Plugin research](../design/research/Plugin%20research%20-%20Obsidian%20best%20practices.md) item 1.

## Manual checks in Obsidian

The e2e suite covers lifecycle, settings, theme, pop-out, language, vault access and navigation. What still needs a person, in a personal vault with the pre-release (0.2.0, not built yet; see [releasing.md](releasing.md)):

1. Run `npm run dev` with `OBSIDIAN_PLUGIN_DIR` set in `.env.local` and look at the view in your own vault, with your theme and community plugins.
2. Use the view with keyboard only and with a screen reader.
3. Check light and dark themes, also third-party ones, and the community colours on each.
4. Check that other plugins and an existing vault carry on as before.
5. Mobile, once `isDesktopOnly` is lifted (after the MVP). `wdio-obsidian-service` can then also emulate mobile.
