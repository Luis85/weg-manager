# Task 14 · Line edits

Phase B. Needs: Task 13.

**Goal.** `NoteStore.update` changes only the frontmatter lines of the keys it sets or removes and leaves every other byte of the file as the user or another tool wrote it: comments, unknown keys in their form, quoting, order, line breaks, a BOM, the body. When it cannot be sure, it writes nothing and says why.

Why not `fileManager.processFrontMatter`: it parses the whole YAML block and writes all of it back. In Obsidian 1.15.1 saving a record after changing one key turned `zip: 01067` into `1067`, `version: 1.10` into `1.1`, rounded a 20-digit number, dropped a comment, rewrote `[a, b]` as a block list, unquoted `'yes'`, saw no block after a BOM (so a BOM note was listed but every save refused), and wrote LF lines into a CRLF note (L6). Why not `getFrontMatterInfo` to find the block: it sees no block after a BOM or with lone carriage returns and does not close at `----`, while the metadata cache does (L7).

## Steps

- [ ] **1. `update(path, change)`** on the port: `change` receives the current frontmatter inside the atomic write and returns a patch (`FrontmatterPatch = { set?, remove? }`) or a typed failure that aborts the write (`FrontmatterChange<E> = (current) => Result<FrontmatterPatch, E>`); a patch that changes nothing writes nothing; what `change` throws is a defect and writes nothing. `applyPatch(target, patch)` says what a patch means on plain data. The Obsidian adapter calls `vault.process(file, fn)`: Obsidian hands `fn` the file's text as it is at that moment, BOM and line breaks included, and writes what `fn` returns, or nothing when it returns the same text. Inside `fn` runs `updateNoteText(text, change, parseYaml)`, which is pure and takes Obsidian's `parseYaml` as an argument. A note deleted between lookup and write makes `vault.process` reject without calling back. Measured in Obsidian 1.15.1 (`note-vanished.e2e.ts`): a note deleted outside Obsidian (a person, Sync, an agent) stays listed until the file watcher reports it a few milliseconds later, and in that window `vault.process` rejects with Node's error, an `Error` with `code: "ENOENT"`, `errno: -2`, `syscall: "open"`. So report `NoteNotFoundError` when the file is no longer at its path **or** the rejection's `code` is `ENOENT` (`isFileGone` in `src/application/notes/command.ts`; only the code counts, never the message text); any other rejection is `NoteWriteError`. The double's `process` does the same (hands over the raw text; writes and fires `modify` only on a change; a callback's throw rejects unchanged; a file deleted meanwhile rejects with the measured error without calling back); `vault.vanish(path)` keeps a file listed while every read and write of it rejects with that error, and `vault.remove(file)` plays the watcher's report. `vanishedScenario` (`tests/support/notes/vanished-scenario.ts`) compares the double with the app (`cachedRead` gives the old text, `read` and `process` reject with `ENOENT`), a contract case checks both adapters, and `note-vanished.e2e.ts` drives the real adapter with the vault held at listing the file (the window is too short to aim at). `trash` and `rename` in that window are not covered: their `ENOENT` can also mean a missing target folder.
- [ ] **2. The refusal.** `WriteRefusal` (`src/domain/notes/write.ts`) = `Schema.Literals(["other-type", "newer-version", "identity", "duplicate-id", "migration-failed", "layout"])`: why a note may not be written at all. This task uses `layout`; Task 15 and Task 17 raise the others. `NoteWriteRefusedError { reason: WriteRefusal }` (`Schema.TaggedError` in `src/application/notes/errors.ts`, in `NOTES_ERROR_TAG_KEYS`), with a title and one `detail` per reason in every notes catalog (`layout` asks the user to write the properties one per line), and its case in `describeNotesError`.
- [ ] **3. Split** (`splitNoteText`) where the metadata cache splits, as measured in Obsidian 1.15.1: after one BOM, a first line `---` (LF or CRLF), up to the next line that starts with `---`. No such line is no block. Measured there: the cache closes the block at **every** line that starts with `---`, whatever follows (`----`, `-----`, `---- `, `--- x`, `---x`, `--- # c`), with LF or CRLF; ` ---` and `...` do not close it. The update writes into a block closed by `---`, by `---` with spaces or tabs after it, or by `----`, and keeps that closing line byte for byte. Every other closing line, lone carriage returns, an opening line that starts with `---` but is not `---` (`----`, `--- x`) and an opening `---` without a line break after it are refused with reason `layout`. An opening `---` followed only by spaces or tabs is no block (nothing is refused, as both of Obsidian's readers see it). Record the closing-line facts in the fidelity scenarios (`vaultFacts`), so the double and Obsidian are compared on them.
- [ ] **4. Read** the block with `parseYaml`: broken YAML or YAML that is no map is `NoteUnreadableError` (without the parser's message, which quotes the note); no block, an empty one or one of only comments and blank lines is `{}`. Then `change` decides on a copy. The metadata cache shows a block of only comments or blank lines like broken YAML (a `yaml` section, no `frontmatter`), so from now on `unreadable` (Task 13 step 9) reads each candidate's text and reports it only when this read fails: what `update` can write into is not unreadable. The candidate is read with `vault.read`, not `cachedRead` (L43): Obsidian keeps the text of every note its cache indexed, also after the note is deleted outside, so `cachedRead` would judge a vanished note by text that is no longer on disk. A candidate deleted outside while the vault still lists it (its `read` rejects with `ENOENT`) is left out; any other failed read is `VaultReadError`. The cost is one disk read for each candidate, and candidates are only the notes whose block the cache could not read.
- [ ] **5. Edit lines** (`editNoteText`): find each top-level key line (plain, `"quoted"` or `'quoted'`) and the lines that continue it (indented lines, block lists also at column 0, block scalars, blank and comment lines between them). A set key's lines are replaced in place; a new key goes before the closing fence; a removed key's lines go; a block left with no line goes with its fences, as Obsidian does. New lines take the opening fence's line break (or the file's first one) and are written by `yamlEntry` (Task 13). A key set to the value it has is left alone. **A comment at the end of a written key line stays**: it goes behind the new value with the blanks the user put before it (`status: open # note` → `status: done # note`); a value that becomes a block list keeps it on the key line (`tags: # list`, then the items). `src/domain/notes/line-comment.ts` finds it: a `#` starts a comment only after a space or tab and outside quoted text, and quoted text starts only where a value starts, so `"A # B"`, `[a, "b # c"]` and `A#B` hold none; comments on further lines of a multi-line value belong to that value and are replaced with it; a value whose quotes do not close on the key line has no comment there; a removed key takes its lines and their comments along. Any other top-level line (a flow mapping, `? key`, `&anchor key`), and keys found by line that differ from the keys YAML read, is `layout`.
- [ ] **6. Check** (the safety net): `parseYaml` of the edited text must read exactly what `applyPatch` makes of the frontmatter before, key order included, every value equal by `Object.is`. Otherwise nothing is written: `NoteWriteRefusedError`, reason `layout`. A save that changes nothing succeeds also for these notes.
- [ ] **7. Folders are found by `clashKey`.** `create` finds its folder segment by segment the way names clash (NFC, then lower case), the type's subfolder too, and writes the path in the vault's spelling: the folder spelled exactly as asked, else the first by code unit among those that clash; from the first segment the vault lacks, the rest is created as asked. `unreadable` finds its folder the same way, and the index (Task 16) looks for unreadable notes in the root folder by `clashKey`. Without this, a vault with `my notes/` and the setting `My Notes` gets a second folder on Linux and, reasoned from how Obsidian's app code creates a file, a failed create on Windows and macOS. Contract cases in `tests/support/notes/contract-folders.ts` (a root folder and its subfolder in another case, the exact one first among several, `unreadable` in the same folder); the check on Windows and macOS is a manual item. The written path still goes through `normalizePath`, so a folder stored in NFD (macOS) is matched but written in NFC. Untested proposal: that Obsidian on macOS then finds the same folder. If it does not (a second folder appears beside the NFD one), write the matched segments in the vault's spelling without `normalizePath` and add a contract case with an NFD folder.
- [ ] **8. Tests, all first:**
  - `tests/unit/domain/notes/note-text.test.ts`, with fast-check: on generated notes every byte outside the patched keys stays; `note-text-comments.test.ts`: the kept trailing comment and where a `#` starts one;
  - `tests/unit/application/notes/note-text.test.ts`: split, read, edit, check, each refusal reason, the two closing-line variants, the kept trailing comment;
  - the byte-fidelity group of `obsidian-note-store.test.ts` on the double: a note with comments, `01067`, `1.10`, a 20-digit number, a flow list, `'yes'`, a quoted key with a comment, a list at column 0 and a block scalar, changed in one key, compared byte for byte; a BOM note keeps its BOM; a CRLF note is written with CRLF;
  - the scenario "note with difficult frontmatter" (`difficultScenario` over `DIFFICULT_NOTES`, against `DIFFICULT_FACTS`), on the double and in `difficult-frontmatter.e2e.ts`: nested maps, block scalars `|` and `>`, multi-line plain and quoted texts, wikilinks in values and lists, `tags`/`aliases` in their forms, comments, duplicate keys, anchors and merge keys, empty values, a BOM with CRLF, tabs, `...`, a block of only comments, YAML that is a text or a list; per note the cache's frontmatter, its `yaml` section, `parseYaml`, the adapter's read, list and unreadable, and what an update does (written, or refused with its reason). This is what showed that the double must parse with the `yaml` package (Task 13 step 12) and that a block of only comments is not unreadable (step 4);
  - `note-write-fidelity.e2e.ts`: 900 generated serialiser lines read back exactly by Obsidian's own `parseYaml` (special numbers included); the block found where the metadata cache finds one (BOM, CRLF, fences, the two closing variants); notes closed by `----` and by `---` with blanks saved with that line kept, and the comment at the end of the written line kept.
