# Task 20 · Release scripts and third-party notices

Phase D. Needs: Task 19.

**Goal.** A version bump that keeps `package.json`, `manifest.json` and `versions.json` in step and a gate step that checks they are; a packaging script that refuses anything but a fresh production build of the tagged version; and a licence file for exactly the third-party code the bundle ships, kept current by the gate.

## Files

Create: `scripts/version-bump.mjs`, `scripts/check-versions.mjs`, `scripts/release-version.mjs`, `scripts/package-release.mjs`, `scripts/bundled-packages.mjs`, `scripts/third-party-notices.mjs`, `scripts/notice-overrides.mjs`, `THIRD-PARTY-NOTICES.txt` (generated), `tests/unit/scripts/{version-bump,check-versions,release-version,package-release,bundled-packages,third-party-notices}.test.ts`. Modify: `configs/vite.config.ts` (the `bundledPackages` plugin), `package.json` (scripts `version`, `check:versions`, `release:package`, `notices`, `check:notices`), `scripts/verify.mjs` (`check:versions` as a fourth check of the first stage, `check:notices` last).

## Steps

- [ ] **1. `bumpVersion(pkgVersion, manifest, versions)`** (`scripts/version-bump.mjs`). Tests first: sets `manifest.version`; adds `versions[new] = manifest.minAppVersion`; keeps existing entries; rejects a version that is not plain `x.y.z` or not greater than the current one. CLI: reads `package.json`, writes both files with two-space JSON and a final newline. Script `version`: `node scripts/version-bump.mjs && git add manifest.json versions.json` (npm's `version` hook). With a protected `main`, bump on a branch with `npm version <x.y.z> --no-git-tag-version`, commit `package.json`, `package-lock.json`, `manifest.json` and `versions.json` as `chore: release <x.y.z>`, merge through a pull request, then start the `Release` workflow on `main` with the input `version`, which creates the tag itself (Task 21 steps 4 and 8), and only when the owner asked for the release. Where direct pushes to `main` are allowed, plain `npm version <x.y.z>` commits and tags `x.y.z` without `v` (`.npmrc`) in one step. Raise `minAppVersion` before a bump whenever the plugin starts using a newer Obsidian API.
- [ ] **2. `packageRelease({ distDir, outDir, rootDir, tag? })`** (`scripts/package-release.mjs`, `RELEASE_FILES = ["main.js", "manifest.json", "styles.css"]`). Tests first: it stages `<outDir>/<plugin-id>/` with exactly the three files and `<outDir>/THIRD-PARTY-NOTICES.txt` **beside** the folder, not inside (the folder a user copies into `<vault>/.obsidian/plugins/<plugin-id>/` stays the three files Obsidian loads); it throws for a missing file, a tag with `v`, a tag that differs from the manifest version, a `dist/` that fails the `check:dist` invariants (a stale or development build), a `versions.json` without an entry for the version or with another `minAppVersion` (the rule of step 6, not a second copy of it), and a missing or empty notices file. Script `release:package`: `node scripts/package-release.mjs` (`--tag x.y.z` in the workflow).
- [ ] **3. Which packages the bundle holds** (`scripts/bundled-packages.mjs`, a Vite plugin enabled for production builds in `configs/vite.config.ts`): after each production build it writes `reports/bundled-packages.json` (not checked in) with the packages of the bundler's module list, the icon collections Nuxt UI turns into `virtual:nuxt-ui-icons` (`@iconify-json/*`, which no module id points at), the packages the plugin's style sheets `@import` (Tailwind, Nuxt UI), and the sha256 of the `main.js` it describes, so a list from an older build is refused. Notices come from the bundle, not from the dependency tree (L35: 248 packages in the runtime tree, 26 in the bundle).
- [ ] **4. The notices** (`scripts/third-party-notices.mjs`, `NOTICES_FILE`, `PACKAGES_FILE`): for each bundled package, its `package.json` licence id and its `LICENSE`, `LICENCE`, `COPYING` and `NOTICE` files from `node_modules/`; packages with the same text share one section; a text that differs (MIT with another copyright line) stays its own section; no version numbers in the file, so a version bump changes it only when a package enters or leaves the bundle or its licence text changes. A package without a licence file gets the standard MIT or ISC text with its `author` as copyright line, and that text is **marked as generated**, because nobody wrote it for the package: `(MIT, licence text generated)` in the index of the file, a line `Licence text: generated from the standard text, the package ships no licence file` in its section (a generated and a shipped text never share a section), and both `notices` and `check:notices` print `licence text generated (no licence file): <names>`, so a new name is read in review against the package's repository. An override that gives its text verbatim is not marked. When that is not possible, or `package.json` has no `license` field, the script fails naming the package, and the way out is an entry with its evidence in `scripts/notice-overrides.mjs` (with this stack two packages need one: `vaul-vue`, whose `package.json` has no `license` field and whose tarball ships no licence file, kept for the day a Drawer enters the bundle, and `@iconify-json/lucide`, which ships no licence file, so its entry holds the `LICENSE` text of the Lucide repository: ISC for Lucide and MIT for the icons derived from Feather). Scripts: `notices`: `npm run build && node scripts/third-party-notices.mjs` (rewrites the file; commit it); `check:notices`: `node scripts/third-party-notices.mjs --check` (regenerates in memory, exits 1 with `THIRD-PARTY-NOTICES.txt is out of date` when it differs, or `run "npm run build" first` when the package list is missing or from another `dist/`). Add `check:notices` as the last step of `SERIAL`, after `build`, because it reads the fresh `dist/`.
- [ ] **5. A new licence is a question.** A licence id that is not MIT, ISC, BSD or Apache, or a copyleft one, goes to the human before the file is committed.
- [ ] **6. Version checks that need no build** (`scripts/check-versions.mjs`, tests first in `check-versions.test.ts`). `versionsEntryProblem(manifest, versions)` (`versions.json` has an entry for the manifest version, equal to its `minAppVersion`; `package-release.mjs` uses it too) and `versionProblems({ packageVersion, manifest, versions, tag? })`: `package.json` and `manifest.json` carry the same version; a `tag`, when given, is a bare `x.y.z` (no `v`) equal to the manifest version; the `versions.json` entry. Each problem is one sentence; the CLI prints `check:versions ✗ <problem>` for each and exits 1, else one `✓` line, and takes `--tag x.y.z`. Script `check:versions`: `node scripts/check-versions.mjs`, a fourth check of the gate's first stage (Task 02 step 7): it reads three JSON files, so it costs nothing, and a version bump that forgot a file fails on the branch, not in the release run. `scripts/release-version.mjs` is the release workflow's "resolve the version" (Task 21 step 4) as a tested script: `resolveReleaseTag({ event, ref, refName, inputVersion })` takes the tag name for a tag start, or, for `workflow_dispatch`, the input, which is only allowed on `refs/heads/main`; the result must match `^[0-9]+\.[0-9]+\.[0-9]+$` as one string (a value with a line break cannot pass) and the input is never echoed; `runResolve(env, tagExists)` reads `EVENT`, `REF`, `REF_NAME`, `INPUT_VERSION`, fails when a start by hand finds the tag already in the clone (`git rev-parse -q --verify refs/tags/<version>`) and writes `tag=<x.y.z>` to `GITHUB_OUTPUT`; the CLI prints one `::error title=Release version::<problem>` and exits 1. Both scripts end with `isCli` (Task 02).

## Checks

- `npm run notices` then `git diff --exit-code THIRD-PARTY-NOTICES.txt` exits 0 on a second run (deterministic).
- Change only `manifest.json`'s `version` and run `npm run check:versions`: it exits 1 and names `package.json` and `versions.json`; revert.
- `npm run build && npm run release:package` writes `release/<plugin-id>/` with exactly three files and `release/THIRD-PARTY-NOTICES.txt`.
- `npm run build -- --mode development && npm run release:package` exits non-zero: a development build fails `check:dist` (on the `main.js` budget: an unminified build with an inline sourcemap is far larger than 1.5 MB; reported: about 9.5 MB). Run `npm run build` afterwards to restore `dist/`.

## Done when

`npm run verify` exits 0 with `check:versions` and `check:notices` in its summary; `npm run verify:full` exits 0. Commit `build: version bump, release packaging and third-party notices`.

With this stack the bundle holds 26 packages, 25 MIT and 1 ISC. Packaging inside the release workflow is first run in Task 21's first release.
