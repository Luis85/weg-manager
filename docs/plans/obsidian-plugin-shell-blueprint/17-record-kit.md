# Task 17 · The record kit

Phase B. Needs: Task 16.

**Goal.** What every record type needs beyond the codec lives in `notes`, in every layer, before any feature exists (L22). A feature then declares its note type, its rules, its texts and its layout, and gets lists, writes, the form's flow, the conflict UI, the delete dialog and the data issues section from `notes`.

## Steps

- [ ] **1. File names** (domain, tests first in `file-name.test.ts`): `recordFileName(title, fallback)`: the title with each run of `\ / : * ? " < > | # ^ [ ]` and control characters replaced by one hyphen, white space collapsed, leading and trailing dots and spaces dropped, `fallback` when nothing is left. `fitsFileName(title, fallback)` with `MAX_FILE_NAME_BYTES = 255`: the file name `recordFileName` gives, with the longest clash suffix ` (100)` and `.md`, has at most 255 bytes in UTF-8 (the limit of Linux and macOS; Windows counts 255 UTF-16 units, never more than the bytes); 100 CJK characters are 300 bytes, so test with three-byte characters. A feature checks it at its title field for a new or changed title only (the tracer's `title.too-long`, Task 18), so a name that is too long is an issue there, never a failed write; a title a record already has is not checked, so a note named so outside the plugin keeps working and is not renamed while its title stays. `followsTitle(fileName, title, fallback)`: the file still carries that name, also with a clash suffix ` (n)`, compared by `clashKey`. A name the user gave the file by hand stays.
- [ ] **2. Form values** (domain, `form.test.ts`, `form-kinds.test.ts`): `lineOfText(max)` (one line of text, no control character, at most `max`). **A form's value follows its field's kind, through one mapping** (`toInput(kind, raw)`, `fromInput(kind, input)`): text for `text`, `date` and `reference`; a number or nothing for `number`; a flag for `checkbox`; a list of text for `list` and `references`. `toInput` shows a value of another kind where the kind can hold it (a number in a text field, one text as a list of one) and an unset or empty property as the kind's empty value; `fromInput` trims text and list entries, drops blank entries, and makes blank text and an empty list unset. `FormInput<F>` is the form's value per field, `formInput(type, frontmatter)` loads a note into it, `draftValues(type, input)` is what a save hands to the rules (`FormDraft<F>`), `trimmedValues(input)` the shortcut for a type of plain text. `editedValues(type, input, draft, loaded)`: a field whose input still equals the loaded value, compared in the form of its kind and structurally, keeps the note's valid value as written (surrounding spaces, a list's order and an id to a missing record included), so an untouched field is never rewritten; every other field is the draft, so a broken value the form shows is repaired by a save. Tests first, per kind: a note loaded through `formInput` and saved untouched through `editedValues` gives back its frontmatter values as written.
- [ ] **3. `defineRecords({ type, title, fallbackName, log, issue?, between? })`** (application). Tests first on the sample type (`record-list.test.ts`, `record-writes.test.ts`, `record-update.test.ts`) with `tests/support/notes/record-fixture.ts` (the index over the sample type, a sequential id generator, `ready`, `indexed`, `stored`, `storedPaths`, under `TestClock`). It gives:
  - `list` and `changes` (a `RecordList` of `RecordRow`: path, file name, id, `editable`, valid values, issues, frontmatter), sorted by title with `localeCompare(…, "<collation-language>", { numeric: true })` and path second; `issue` adds the data a sentence needs to the codec's issue; `between` adds issues between records over the sorted rows (for example a duplicate title); `toList`; `shownName` (the title, else the file name); `names` and `nameChanges`, the shown name of each record by its id through the snapshot's `byId` (the pair `useStream` takes), for references to this type; `shownReference(names, id)` gives the name, or the id while no record carries it;
  - `create(values)`: an id from `IdGenerator`, the note in `recordFolder(rootFolder, type)` named by `recordFileName`, a taken name with ` (2)`;
  - `update(row, values)`: `NoteStore.update(path, editChange(type, row.frontmatter, values))`, then the file follows the title while `followsTitle` holds for the old name, up to ` (100)`; save and rename run **uninterruptibly as one command**; a rename that fails keeps the saved note and logs `<log>.rename.failed` (`warn`, no data); a rename that succeeds returns the note the update wrote at the path of the rename (`{ ...written, path }`), never the frontmatter the rename read, because a rename that joined another one returns before the cache has indexed the save (Task 13 step 9);
  - `remove(row)`: `NoteStore.trash`;
  - update and remove find a note renamed meanwhile **by its id**, through the snapshot's `byId` (Task 16); while another note carries the same id, both are read-only and a write fails `NoteWriteRefusedError { reason: "duplicate-id" }`;
  - every successful write is confirmed by an `info` notice from the notes catalog (`notices.created`, `saved`, `deleted`, by the title): a toast confirms a short-lived success; a failure stays at the form.
- [ ] **4. Texts** (`record-texts.test.ts`): `describeRecordIssue(issue, notes, texts)` words a feature's issues from its `RecordTexts` (`fields` labels, optional `missing`, `issues: IssueSentences<Issue>`); the record issues and field kinds' codes are the notes catalog's. The generic texts (notices, conflict, delete dialog, "Open in Obsidian", data issues) carry no feature words.
- [ ] **5. `useRecordForm({ type, record, initial, create, update, invalid, rules, describe, labels, summary, root, done })`** (presentation, TanStack Form). The options: `type` the note type; `record` the `RecordRow` being edited, `undefined` to create one; `initial` start values of a new record beside the empty ones; `create(input)` and `update(row, input)` the feature's use cases as `UseCaseFn`s, each resolving to the note as written (`{ frontmatter }`); `invalid` the `_tag` of the feature's error whose `issues` land at their fields (the tracer's `InvalidItemError`); `rules(input)` the feature's rules for the input as it stands; `describe(issue)` an issue in the feature's words (`describeRecordIssue` with its texts); `references` (optional) the `ReferenceSource` of the type each reference field points at; `labels` each field's label, which the conflict's legend uses; `summary` the `{ title, detail }` a failed submit shows at the top of the form; `root()` the form's root element, in which the focus moves to the first field with `aria-invalid`; `done(id)` called with the id of the record that was saved. It gives: each field loaded in the form of its kind (`formInput`); validators that call the feature's `rules` (which call the domain rule, global constraint 15); the use case's issues placed at their fields; a failed submit shows a summary with `role="alert"` at the top and moves the focus to the first field with `aria-invalid`; the note's own issue shown at its field until the field changes (also `reference.missing`, which never blocks a save); Save `aria-disabled` while blocked, never `disabled` (L30); **the conflict loop**: on `NoteEditConflictError` the form shows `ConflictChoice` with, per field, the value when the form opened, the user's and the note's current one; each value shown by its kind (`shownValue` in `conflict.ts`: a flag as yes or no, a list with its entries, a referenced record by its shown name through `references`, the id while none carries it, unset and an empty list as "empty"); the user picks one per field, and "theirs" sets the form value through `formInput`; applying ends the conflict view, a chosen value that breaks a rule stays in the form with its issue, and the next save goes against the same current values (the conflicting fields of `loaded` replaced by `current`). The conflict takes the focus to its heading (`tabindex="-1"`). **Unsaved input:** the form reports TanStack's `isDirty` to the screen around it through `useSheetGuard` (`false` when it unmounts); outside a record screen the report does nothing.
- [ ] **6. `useRecordScreen({ type, list, root })`**: the folder for the intro text, loading only after 300 ms (`useDelayed`), the index's failure with a retry (`ErrorNotice` with `rebuildNoteIndex`; `tests/dom/presentation/notes/index-failure.test.ts`), the empty state, the sheet and the delete dialog with their modal props (`useModal`), **the question before unsaved input is discarded** (`provideSheetGuard` collects the form's report; `requestClose` closes the sheet at once without unsaved input, else opens `DiscardInputDialog`, whose `keep` returns to the form and whose `discard` closes the sheet), and the focus after them (`useFocusAfter`): to the saved or created card's edit button once the index shows the card (else its heading), back to the opener on cancel, to the create button once a deleted card has left the list. Cards carry `data-card-key` = `cardKey(row)` (the id, or the path for a note without an id of its own) so a card survives the rename of its file; focus targets carry `data-focus="edit" | "remove" | "name" | "add"`.
- [ ] **7. Components.** `DeleteRecordDialog` (a `UModal` that asks first, initial focus on Cancel, runs the feature's delete as a command, title from the feature, the rest from the notes catalog); `OpenNoteButton` ("Open in Obsidian" through `openNote`, on every read-only record and every data-issue note, so a note the plugin cannot write can be repaired by hand); `ConflictChoice`; `RecordSheet` (`<RecordSheet :title :state>` with the form in its `body` slot: a `USlideover` that passes `dismissible: false` while the form is dirty, so Escape and a pointer-down outside emit `close:prevent` instead of closing, and sends them, its close control and the form's cancel to `requestClose`); `DiscardInputDialog` (a `UModal`, "Discard input?", opened with the focus on "Keep editing" (`data-autofocus`), the safe default, and a "Discard" button). Without changes and after a save the sheet closes without a question. Tests: `discard-input.test.ts` (each way to close, with and without input, the default focus) and `record-form-kinds.test.ts` (a form of every kind: untouched fields keep their stored value, a list and a flag edited, the conflict shows each kind).
- [ ] **8. The data issues section.** `DataIssues.vue` lists the unindexed notes (`unindexedChanges` with `useStream`, worded by `describeUnindexedIssue`, each with `OpenNoteButton`); `DataIssuesBadge.vue` counts them beside the section's label. `src/presentation/notes/screens.ts`: `{ screens: {}, sections: { "data-issues": { label, component: () => import("./components/DataIssues.vue"), badge: () => import("./components/DataIssuesBadge.vue") } } } satisfies ModuleScreens<"notes">`. Test: `tests/dom/presentation/notes/data-issues.test.ts` (the section, the app's navigation with its badge; the badge arrives after the list, so wait for it, L10). Whether readable records with an issue of their own (a duplicate id, a newer version) are also listed here is decided with the second record type.
