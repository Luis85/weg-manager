# Task 04 · The Obsidian test double

Phase A. Needs: Task 02.

**Goal.** An in-memory double of the parts of the `obsidian` API the shell uses, so lifecycle, commands, settings tab and views run in Vitest. It copies Obsidian's behaviour, including the surprising parts this plan names; the vault half (vault, metadata cache, file manager) comes in Task 13 with the fidelity scenarios that compare it with real Obsidian (L31).

## Files

Create under `tests/support/obsidian/`: `index.ts`, `component.ts`, `events.ts`, `plugin.ts`, `app.ts`, `workspace.ts`, `views.ts`, `ribbon.ts`, `settings.ts`, `notice.ts`, `dom.ts`, `language.ts`, `paths.ts`, `conformance.ts`, `real.ts`, and `local-storage.ts` only with step 10. Create `tests/support/dom-setup.ts`, `tests/unit/support/obsidian-double.test.ts`, `tests/unit/support/test-manifest.test.ts`, `tests/dom/obsidian-guard.test.ts`.

Install (`devDependencies`): `happy-dom`. (`obsidian` is installed since Task 02.)

## Steps

- [ ] **0. The `dom` project.** Add it to `configs/vitest.config.ts` now (Task 02 step 6) with `setupFiles: ["tests/support/dom-setup.ts"]`; its first test is `tests/dom/obsidian-guard.test.ts`.
- [ ] **1. Opt-in.** A suite that needs the double writes `vi.mock("obsidian", () => import("@test/obsidian"))`; without it the Task 02 guard throws. Turn the `it.todo` alias case of `tests/unit/obsidian-guard.test.ts` into a test (`await import("@test/obsidian")` gives a `Plugin` function) and add the same pair of cases for the dom project (`tests/dom/obsidian-guard.test.ts`).
- [ ] **2. `Component`** with Obsidian's semantics: `load()`; `unload()` calls `onunload`, then runs `register` callbacks and releases `registerEvent` refs in reverse order; `registerDomEvent`, `registerInterval`. Test each order.
- [ ] **3. `Events`** with `on`, `off`, `offref` (by identity; an unknown or already removed ref is ignored, as in Obsidian), `trigger(name, ...args)`, and the test helper `listenerCount(name?)`.
- [ ] **4. `Plugin extends Component`** with `app`, `manifest`, `loadData`, `saveData`, `addCommand` (the id is prefixed `<plugin-id>:` as Obsidian does), `removeCommand`, `addRibbonIcon`, `addSettingTab`, `registerView`, `onExternalSettingsChange`; registrations are cleared by `unload()`. `TEST_MANIFEST` repeats `manifest.json`'s `id`, `minAppVersion` and `isDesktopOnly` (`tests/unit/support/test-manifest.test.ts` pins them equal). `createTestPlugin(PluginClass, options?)` returns `{ plugin, registry }`; `registry` exposes `commands`, `views`, `settingTabs`, `ribbonIcons`, `notices`, `saved`, `runCommand(id)`, `load()`, and the knobs `failNextAddCommand({ after? })`, `setFailLoadData`, `holdLoadData`/`releaseLoadData` (for "unload while load is pending"), `writeExternally(data)` (a `data.json` changed outside, as Sync does).
- [ ] **5. Ribbon** (`ribbon.ts`) as Obsidian 1.15.1 keeps it: entries in `app.workspace.leftRibbon.items` keyed `<plugin-id>:<title>`; `icon.remove()` removes the element but leaves the entry, which comes back on the ribbon's next `onChange()` (L27); a normal `unload()` releases the entry (`Plugin.addRibbonIcon` registers the release): the entry stays in `items` without `buttonEl` and `callback`, so its order and hidden state survive a re-enable, and a check that counts the plugin's entries counts only those that still have a button or a callback.
- [ ] **6. Workspace and views.** `App.workspace` is an `Events` with `layoutReady` (default `true`), `markLayoutReady()`, `onLayoutReady(cb)` (runs at once when ready), `getLeavesOfType`, `getLeaf(mode)` recording each mode in `workspace.leafRequests`, `revealLeaf`, `requestSaveLayout` counted in `workspace.layoutSaves`. Tabs as Obsidian 1.15.1 keeps them in one tab group: the workspace starts with an active new tab (`empty`); `getLeaf(false)` is the active leaf when it is navigable (a new tab, a note), else a new tab; `getLeaf(true)` and `"tab"` reuse the active leaf while it is a new tab, else open one, which becomes active; `revealLeaf` brings a leaf to the front and builds a deferred view without changing the active leaf; `changeLayout(getLayout())` closes every view and restores the tabs with only the active one built and the others **deferred** (`isDeferred`, a stand-in view that keeps the type and the saved state with an empty container, built by `loadIfDeferred`, `revealLeaf` or `setViewState`, which then gets the state given, not the saved one); `getActiveViewOfType(View)`. `WorkspaceLeaf` with `openIn(document)` to simulate a pop-out, `setViewState` as in Obsidian 1.15.1 (a new view type opens the view, then the view gets the state; an open view of the same type is kept and only gets the new state), `openFile` recorded in `leaf.openedFiles`. `View`/`ItemView` with `contentEl`, `getState`/`setState`, `navigation` (default `false`), `onOpen`/`onClose`, and Obsidian's order: `onOpen` runs before `setState`.
- [ ] **7. Settings.** `PluginSettingTab` with the declarative API (`getSettingDefinitions`, `getControlValue`, `setControlValue`, `update()`, Obsidian 1.13 and later) and a renderer `settingsIn(tab)` that tests read; `Setting`, `TextComponent`, `ToggleComponent`, `DropdownComponent` for what the renderer builds; a `pending` handle that settles after each change, so tests wait on it, not on a timer (Task 09, *Waiting*).

- [ ] **9. - [ ] **10. Local storage** (`local-storage.ts`, on `App`): `loadLocalStorage(key)`/`saveLocalStorage(key, value)` storing JSON per vault; a falsy value clears the key, as Obsidian does; a broken entry reads as `null`; `app.localStorage.setRaw` plants a raw entry. ## Rules for the double

- **Copy Obsidian, not an ideal.** Each behaviour above was measured in Obsidian 1.15.1; the ribbon is compared with real Obsidian by `lifecycle.e2e.ts` and `setViewState` by `navigation.e2e.ts` (Task 12). Where a later e2e spec (Task 12, Task 13) finds a difference, change the double and keep the expectation (L31).
- **Typed against the real API** (`conformance.ts`). Each class of the double declares `implements Uses<Obsidian.X, "the members the plugin uses">`, where `Uses<Real, K>` maps each member through `Doubled<T>`, which reads a real signature with Obsidian's classes (`TFile`, `TFolder`, `WorkspaceLeaf`, `View`, `Vault`, `App`, `Plugin`, `EventRef`, …) swapped for the double's, in parameters and results too; function types compare strictly, so a missing member or a differing parameter or result fails `npm run typecheck`. Free functions and constants carry `typeof Obsidian.f`. Overloaded members (a mapped type sees only the last overload) and protected ones are left out, each named in a comment, as is any member whose measured result differs from the d.ts (`trashFile` resolves `true` where the d.ts says `void`). Plugin code is handed the double through one module, `real.ts` (`asObsidian(app)`, `asObsidianPlugin`, `asObsidianWorkspace`, `asObsidianLeaf`, and back `asDoubleView`, `viewOf`), the only place that casts; tests never write `as never` at a call.
- fallow's `unused-class-members` rule is off for `tests/support/obsidian/**` (Task 03): the double mirrors an API, not only what today's tests call.

## Done when

`npm run verify` exits 0, the guard tests pass in both projects, and the double's own tests pass. Commit `test: obsidian test double`.
