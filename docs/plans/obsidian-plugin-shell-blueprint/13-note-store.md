# Task 13 · The note store

Phase B (skip for a plugin without note data). Needs: Task 12.

**Goal.** Every feature reaches the vault through one port in domain terms, `NoteStore`. Its Obsidian adapter is the only code that changes vault files; an in-memory adapter serves the tests and the harness; one contract suite runs against both; the same suite also runs inside real Obsidian through a probe plugin; fidelity scenarios run the same steps on the double and in real Obsidian and compare them with one expectation (L31). This task builds reads, create, rename, trash, the opener and the host's file events; Task 14 builds `update`.

## Steps

- [ ] **1. The root folder setting** (`src/domain/shell/root-folder.ts`, a second `FIELDS` entry): `rootFolder`, default `<root-folder>`, `omitWhenDefault: true`, issue `rootFolder.invalid` with `max: ROOT_FOLDER_MAX_LENGTH` (100). Stored normalised: trimmed, no leading or trailing slash, `/` between names; no empty name; no name that starts with a dot (Obsidian does not index hidden folders, so notes there would never be listed; this also covers `.`, `..` and the config folder); none of `* " \ < > : | ?` and no control character. It has no UI (one edit location: a power user edits `data.json`). Test: `settings-root-folder.test.ts`.
- [ ] **2. The port** (`src/application/notes/ports.ts`), plain data, never `TFile`. `Frontmatter = Readonly<Record<string, unknown>>` (in `src/domain/notes/note-type.ts`, which Task 15 fills with the type declarations); a note is `Note = { path, frontmatter }`:
  | Call | Does |
  | --- | --- |
  | `list` | every record: a Markdown note whose frontmatter `schema` starts with `<plugin-id>.` (`isRecordFrontmatter`, step 6), anywhere in the vault, sorted by path, from the metadata cache, no file contents |
  | `read(path)` | one note; `{}` for no frontmatter or broken YAML |
  | `unreadable(folder)` | the paths of Markdown notes in `folder` or below whose frontmatter block cannot be read, sorted |
  | `create({ folder, name, frontmatter, body? })` | missing folders and the note in one `vault.create`, with the text of `newNoteText` (step 7); a taken name gets ` (2)`, ` (3)`, … up to `MAX_NAME_ATTEMPTS` (100) |
  | `update(path, change)` | Task 14 |
  | `trash(path)` | `fileManager.trashFile`, so the user's *Deleted files* setting applies; a failed move is `NoteTrashError`: a rejection, and a result of `false`, which Obsidian 1.15.1 resolves without rejecting when the system trash fails, and then keeps the note (L42) |
  | `rename(path, newName)` | `fileManager.renameFile` in the same folder, so Obsidian updates links; another note's name is `NotePathTakenError`; the note's own name in another case is allowed; returns the note at its new path with the frontmatter as the store reads it after the move |
  Beside it: `NoteOpener.open(path)` (use case `openNote`: `workspace.getLeaf("tab").openFile(file, { active: true })`, so the plugin's fixed tab stays; no Markdown note there is `NoteNotFoundError`, and so is an `openFile` that rejects after the note left the vault or with `ENOENT`; any other rejection is `NoteOpenError`, a failure of Obsidian the user can retry, not a defect) and `IdGenerator` (`crypto.randomUUID()` in the plugin, `sequentialIdGenerator()` in tests and the harness).
- [ ] **3. Errors** (`src/application/notes/errors.ts`, each named in `NOTES_ERROR_TAG_KEYS`, the manifest's `errors.tags`): `NoteNotFoundError` (also for a note deleted between lookup and write), `NotePathTakenError`, `InvalidNoteNameError` (issue `empty`, `forbidden-character` or `leading-dot`), `NoteUnreadableError`, `NoteWriteError` (the vault call failed; never for a throw of the plugin's own code, which `asDefect` turns into a defect), `NoteTrashError` (the user reads "not deleted", not "not saved"), `NoteOpenError` (Obsidian could not open the note in a tab); reads fail with the shell's `VaultReadError`. None carries a path. Texts in the notes catalog (`describeNotesError`). Later tasks add `NoteWriteRefusedError` (Task 14), `NoteEditConflictError` (Task 15) and `NoteIndexReadError` (Task 16).
- [ ] **4. Writes are commands** (`src/application/notes/command.ts`): `writeCommand` runs the vault calls in `Effect.uninterruptible`, so once started they complete even when the caller is interrupted (L4); checks that write nothing (name, free path, note exists) run before it. `trashCommand` does the same for a trash and also fails when the move resolves `false` (L42; only `false`, never `undefined`), `createNote` for a create, and `asDefect(run)` turns a throw of the plugin's own code into a defect. Test: `command.test.ts`.
- [ ] **5. Name clashes** (`src/domain/notes/notes.ts`): `clashKey(name) = name.normalize("NFC").toLowerCase()`, `clashName(name, attempt)` (` (2)` and up), `MAX_NAME_ATTEMPTS = 100`, `NoteNameIssue` and `noteNameIssue(name)` (the issues of step 3). Two names clash when their keys are equal: NFC first because macOS writes umlauts decomposed; `toLowerCase`, not `toLocaleLowerCase` or `localeCompare`, because it is Unicode's default case mapping, the same in every locale and engine. The store compares a candidate with every file **and folder** in the target folder (`TFolder.children`), because Obsidian's lookups by path are case-sensitive and a Linux disk would take both names; Windows and macOS would not.
- [ ] **6. The schema marker** (`src/domain/notes/schema-marker.ts`): `RECORD_SCHEMA_PREFIX = "<plugin-id>."`; a record's frontmatter has `schema: <plugin-id>.<type>/v<n>`, `<type>` kebab-case letters (an English singular), `<n>` a positive integer without a leading zero. `parseSchemaMarker(value)` says `none` (no string with the prefix), `malformed` (the prefix, not this form) or `record` with type and version. `isRecordFrontmatter(frontmatter)` (in `notes.ts`) is "not `none`", so `list` also returns a note with a broken marker, to be shown with `schema.malformed`. Where a note lies does not matter: people and agents may move notes freely. Test: `schema-marker.test.ts`.
- [ ] **7. One serialiser** (`yamlEntry(key, value, eol)` in `src/domain/notes/yaml-text.ts`; `newNoteText(frontmatter, body)` in `src/domain/notes/note-text.ts`, re-exported by `src/application/notes/note-text.ts`). `create` writes with it now, and every update of Task 14 does too. Text is written plain only where YAML 1.2 (Obsidian) and YAML 1.1 (older tools an agent may use) read it back as that same text; `01067`, `1.10`, `yes`, `12:30`, `""` and text with `: `, ` #`, an indicator first, or spaces around are double-quoted; characters that are not printable or that some reader takes as a line break (NEL, LS, PS, BOM) are escaped. Dates stay plain, as Obsidian writes them. A nested map or `undefined` is a defect: no record holds one. `newNoteText` writes `---`, one `yamlEntry` per defined value in order, `---`, then the body; with no value, the body alone. Tests first in `yaml-text.test.ts` with fast-check: every written value reads back exactly through the `yaml` package in 1.2 and in 1.1 mode.
- [ ] **8. The adapter kit** (`src/application/notes/adapter.ts`, the second entry, imported only by `src/infrastructure/**`): `asDefect`, `createNote`, `trashCommand`, `writeCommand`, `copyFrontmatter`, `recordNotes`, `newNoteText`, `pathsInFolder`, `planRename`, and from Task 14 `updateNoteText`. The kit imports the rest of the module through its `index.ts`; the module's other files never import the kit. ESLint: `kitOutside` refuses `notes/adapter` everywhere but `src/infrastructure/**`, `kitElsewhere` refuses any other layer's `notes/adapter` there. fallow: the zone `application/notes-adapter` (`adapter.ts`, `command.ts`, `frontmatter.ts`, `note-text.ts`, `paths.ts`) with `adapter.ts` its only public file, importable only by `adapters`, `adapters/notes` and `memory`.
- [ ] **9. The Obsidian adapter** (`src/infrastructure/obsidian/notes/note-store.ts`): `vault.create`, `vault.createFolder`, `vault.process` (Task 14), `fileManager.trashFile`, `fileManager.renameFile`, every path through `normalizePath`; `NoteOpener` calls `openFile` through `tryPromise`, so a rejection is a typed error; no `vault.modify`, no `vault.adapter`, no `read` followed by a write, no `fileManager.processFrontMatter` (L6). **The cache lags** a write by a few milliseconds: right after `create`, `getFileCache` is `null`; right after an update it holds the old frontmatter. So every write returns the note as written, and `list`/`read` show what the cache holds (L9). `rename` is the exception that needs no care: Obsidian runs the move only after its cache has indexed every earlier write, so a rename right after an update returns the written frontmatter (measured; contract cases "returns the frontmatter an update just wrote" and "a create just wrote" hold every adapter to it); a rename that joined another rename (a known gap, README) returns before its own move with the cache's frontmatter of that moment, which is why the record kit (Task 17) returns the frontmatter its own update wrote. **Unreadable frontmatter** (measured in Obsidian 1.15.1): broken YAML or YAML that is no map leaves the cache without `frontmatter` and `frontmatterPosition`, like a note without a block; only `sections` tells them apart (a `yaml` section from line 0 to the closing fence). A note with a `yaml` section but no `frontmatter`, unless the section is just two fences, is a candidate; Task 14 step 4 makes `unreadable` read each candidate's text before it reports it.
- [ ] **10. The in-memory adapter** (`memoryNoteStore()`, `src/infrastructure/memory/notes/`): notes as data, not text (byte fidelity is the Obsidian adapter's). Handles: `seed(path, frontmatter | "none" | "broken", body)`, `removeOutside(path)`, `body`, `isFolder`, `setFailReads`, `setFailWrites`, `holdWrites`/`releaseWrites`/`heldWrites`, and `opener` (records `opened()`). Reads see writes at once. Built where an `EventBus` is, it publishes the same file events for its writes and seeds that `hostEventsLayer` publishes for the Obsidian adapter. `tests/support/notes/store-events.ts` holds that list: `STORE_EVENT_STEPS`, each step a `name`, a `run(store, seed)` effect and the `AppEvent`s the bus carries for it, in order: a create (`FileCreated`, `MetadataChanged`), a rename (`FileRenamed`), a trash (`FileDeleted`), a note seeded from outside (`FileCreated`, `MetadataChanged`) and an outside edit of a seeded note (`FileModified`, `MetadataChanged`); folders are not published. Task 14 adds an update (`FileModified`, `MetadataChanged`) and an update that changes nothing (no event). Both sides are checked against the list (`memory-note-store-events.test.ts`, `tests/dom/infrastructure/notes/store-events.test.ts`). Every made-up failure carries `TEST_ONLY_MARKER = "<plugin-id>/test-only"`; `check:dist` rejects a `main.js` that holds it (a planted import of the in-memory store into `appLayer` must fail `check:dist`, ESLint and fallow). Nothing in `src/` imports `memory/`.

On the double: `tests/unit/support/obsidian-double.test.ts` and, for the workspace with the real plugin loaded, `tests/dom/workspace-fidelity.test.ts`; in Obsidian: `note-store.e2e.ts` and `workspace.e2e.ts`. A difference is a bug in the double: fix the double, never the expectation alone. What a scenario shares comes through the probe (`ScenarioProbe` in `scenario-context.ts`: the adapter's `api`, the event `recorder`, `workspace.openRoute`), which the double's tests build with `doubleProbe(app)`. `executeObsidian` serialises a scenario and sorts the keys of what it returns, turning `undefined` into `null`, so scenarios use only their arguments, return plain JSON and show key order through file texts.
  - **Steps end on a fence, never on a settle time** (`recorder.ts`, `eventRecorder(app, options)`): a step's events are recorded in order until `fence()` has written a new text into a sentinel note and seen that text's `changed`, the sentinel's `resolve` and the `resolved` after it. Obsidian's metadata cache parses and resolves files in the order they were written, so by then every event of the step has fired, however late (measured in 1.15.1: `resolve` may lag behind the next file's `changed`, so the fence waits for the sentinel's `resolve`). `done` marks where a step's promise settled. Only the vault's own writes can be fenced; the file watcher's report of an outside change comes on its own time.
  - **Orders are asserted.** Pin every order Obsidian keeps over several runs, idle and beside busy processes. Measured in 1.15.1 over nine runs: a write's vault event before its promise settles and the cache's `changed` after it; `resolve` and `resolved` after `changed`; a rename's and a trash's `resolved` after their promise; parents first for `createFolder`; parallel creates indexed in the order made; folder rename and trash in the vault's order. Write an order Obsidian changes from run to run as `eitherOrder(first, second)` (`event-order.ts`; `inExpectedOrder(report, expected)` puts such a pair into the written order only when the report holds exactly those events one way round, so any other difference still fails): whether a new file is indexed before or after a write directly after its create (one run in nine the write came first), and whether `processFrontMatter`'s index or a read after it comes first. Leave out, and say so in the step, what has no stable count or order: how many `resolved` files indexed together get, and `resolve` and `resolved` of a file written again at once.
