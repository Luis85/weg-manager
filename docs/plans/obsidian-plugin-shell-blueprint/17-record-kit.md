# Task 17 · The record kit

Phase B. Needs: Task 16.

**Goal.** What every record type needs beyond the codec lives in `notes`, in every layer, before any feature exists (L22). A feature then declares its note type, its rules, its texts and its layout, and gets lists, writes, the form's flow, the conflict UI, the delete dialog and the data issues section from `notes`. In the source repository this code first grew inside the first feature and was moved out after a review found that the second type would have copied it.

## Steps

- [ ] **1. File names** (domain, tests first in `file-name.test.ts`): `recordFileName(title, fallback)`: the title with each run of `\ / : * ? " < > | # ^ [ ]` and control characters replaced by one hyphen, white space collapsed, leading and trailing dots and spaces dropped, `fallback` when nothing is left. `fitsFileName(title, fallback)` (and `MAX_FILE_NAME_BYTES`): the file name with ` (100)` and `.md` has at most 255 bytes in UTF-8 (Task 14 step 7); the feature's rules check it at the title field for a new or changed title only (the source's communities give `name.too-long`). `followsTitle(fileName, title, fallback)`: the file still carries that name, also with a clash suffix ` (n)`, compared by `clashKey`. A name the user gave the file by hand stays.
- [ ] **2. Form values** (domain, `form.test.ts`): `lineOfText(max)` (one line of text, no control character, at most `max`); `trimmedValues(input)`; `editedValues(type, input, draft, loaded)`: a field whose input is still the loaded text keeps the note's valid value as written, surrounding spaces included, so an untouched field is never rewritten.
- [ ] **3. `defineRecords({ type, title, fallbackName, log, issue?, between? })`** (application). Tests first on the sample type (`record-list.test.ts`, `record-writes.test.ts`, `record-update.test.ts`) with `tests/support/notes/record-fixture.ts` (the index over the sample type, a sequential id generator, `ready`, `indexed`, `stored`, `storedPaths`, under `TestClock`). It gives:
  - `list` and `changes` (a `RecordList` of `RecordRow`: path, file name, id, `editable`, valid values, issues, frontmatter), sorted by title with `localeCompare(…, "<test-language>", { numeric: true })` (the source fixes German collation; pick the product's primary language) and path second; `issue` adds the data a sentence needs to the codec's issue; `between` adds issues between records over the sorted rows (for example a duplicate title); `toList`; `shownName` (the title, else the file name);
  - `create(values)`: an id from `IdGenerator`, the note in `recordFolder(rootFolder, type)` named by `recordFileName`, a taken name with ` (2)`;
  - `update(row, values)`: `NoteStore.update(path, editChange(type, row.frontmatter, values))`, then the file follows the title while `followsTitle` holds for the old name, up to ` (100)`; save and rename run **uninterruptibly as one command**; a rename that fails keeps the saved note and logs `<log>.rename.failed` (`warn`, no data);
  - `remove(row)`: `NoteStore.trash`;
  - update and remove find a note renamed meanwhile **by its id**; while another note carries the same id, both are read-only and a write fails `NoteWriteRefusedError { reason: "duplicate-id" }`;
  - every successful write is confirmed by an `info` notice from the notes catalog (`notices.created`, `saved`, `deleted`, by the title): a toast confirms a short-lived success; a failure stays at the form.
- [ ] **4. Texts** (`record-texts.test.ts`): `describeRecordIssue(issue, notes, texts)` words a feature's issues from its `RecordTexts` (`fields` labels, optional `missing`, `issues: IssueSentences<Issue>`); the record issues and field kinds' codes are the notes catalog's. The generic texts (notices, conflict, delete dialog, "Open in Obsidian", data issues) carry no feature words.
- [ ] **5. `useRecordForm({ type, record, initial, create, update, invalid, rules, describe, labels, summary, root, done })`** (presentation, TanStack Form): validators that call the feature's `rules` (which call the domain rule, global constraint 15); the use case's issues placed at their fields; a failed submit shows a summary with `role="alert"` at the top and moves the focus to the first field with `aria-invalid`; the note's own issue shown at its field until the field changes; Save `aria-disabled` while blocked, never `disabled` (L30); **the conflict loop**: on `NoteEditConflictError` the form shows `ConflictChoice` with, per field, the value when the form opened, the user's and the note's current one; the user picks one per field; applying ends the conflict view, a chosen value that breaks a rule stays in the form with its issue, and the next save goes against the same current values (the conflicting fields of `loaded` replaced by `current`). The conflict takes the focus to its heading (`tabindex="-1"`).
- [ ] **6. `useRecordScreen({ type, list, root })`**: the folder for the intro text, loading only after 300 ms (`useDelayed`), the index's failure with a retry (`ErrorNotice` with `rebuildNoteIndex`; `tests/dom/presentation/notes/index-failure.test.ts`), the empty state, the sheet and the delete dialog with their modal props (`useModal`), and the focus after them (`useFocusAfter`): to the saved or created card's edit button once the index shows the card (else its heading), back to the opener on cancel, to the create button once a deleted card has left the list. Cards carry `data-card-key` = `cardKey(row)` (the id, or the path for a note without an id of its own) so a card survives the rename of its file; focus targets carry `data-focus="edit" | "remove" | "name" | "add"`.
- [ ] **7. Components.** `DeleteRecordDialog` (a `UModal` that asks first, initial focus on Cancel, runs the feature's delete as a command, title from the feature, the rest from the notes catalog); `OpenNoteButton` ("Open in Obsidian" through `openNote`, on every read-only record and every data-issue note, so a note the plugin cannot write can be repaired by hand); `ConflictChoice`.
- [ ] **8. The data issues section.** `DataIssues.vue` lists the unindexed notes (`unindexedChanges` with `useStream`, worded by `describeUnindexedIssue`, each with `OpenNoteButton`); `DataIssuesBadge.vue` counts them beside the section's label. `src/presentation/notes/screens.ts`: `{ screens: {}, sections: { "data-issues": { label, component: () => import("./components/DataIssues.vue"), badge: () => import("./components/DataIssuesBadge.vue") } } } satisfies ModuleScreens<"notes">`. Test: `tests/dom/presentation/notes/data-issues.test.ts` (the section, the app's navigation with its badge; the badge arrives after the list, so wait for it, L10). Whether readable records with an issue of their own (a duplicate id, a newer version) are also listed here is decided with the second record type in the source.
