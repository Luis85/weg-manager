# Testing

Tests come first. Each behaviour step writes the failing test, sees it fail, then implements. A "discriminating check" counts only once it has been seen to fail on a planted defect. `npm run verify` runs the unit and dom projects with coverage; the end-to-end suite and mutation testing run on their own (see the end-to-end section).

## Projects

| Project | Files | Environment | Use for |
| --- | --- | --- | --- |
| `unit` | `tests/unit/**/*.test.ts` | node | domain, application, scripts, harness layers, logging |
| `dom` | `tests/dom/**/*.test.ts` | happy-dom + Vue/Nuxt UI plugins | lifecycle, settings tab, views, components |
| e2e | `tests/e2e/specs/*.e2e.ts` | real Obsidian (WebdriverIO) | see [End-to-end tests](#end-to-end-tests-in-obsidian) |

Tests mirror the module folders: `tests/<project>/<layer>/<module>/`, e.g. `tests/unit/application/shell/` for `src/application/shell/`. Tests of the composition (plugin load through `main.ts`, `bootstrap.ts`, the files at a layer root) stay above them, e.g. `tests/dom/lifecycle.test.ts`.

- Run one file: `npx vitest run tests/dom/presentation/communities/screen.test.ts`
- Run one project: `npx vitest run --project unit`
- Run tests by name: `npx vitest run -t "read-only"`

Coverage (`npm run test:coverage`) applies to `src/**` and enforces lines 90, statements 90, functions 90 and branches 85.

## Waiting and timing

The unit and dom projects run on loaded machines: the gate beside another suite, Stryker with several runners, CI. A test that holds on an idle laptop must not fail there.

- **No wall-clock assertion.** A bound on elapsed time, and above all a ratio of two times, fails on a slow machine for no reason in the code. Assert counted work instead: reads of the `NoteStore`, decodes of notes (`note-index-budget.test.ts` counts both: a build decodes each record once, a rebuild decodes nothing unchanged, one edit costs one read and one decode). Time belongs to the e2e specs, which record it in `reports/e2e/`.
- **Waits use `eventually`**, never a bare `vi.waitFor`, whose default budget is 1 s. A wait that succeeds returns at once, so the 4 s budget costs nothing; it stays under the 5 s test timeout, so a wait that never succeeds fails with its own assertion. The poll interval is 10 ms.
- **Wait on a condition, not on a guess.** Prefer a handle that settles (`tab.pending` on the settings tab double) or a count that proves the work ran (`event-listeners.test.ts` waits until the first runtime's finalizer has called `offref` again) over `setTimeout(n)`. A timer is acceptable only to prove that nothing happens (`icons-offline.test.ts`: no request after Iconify's batch timer).
- **Preload what a view imports.** The first mount of a surface imports Vue, Nuxt UI and, through `appSurface`, the shell's settings screen and the whole communities and notes modules: a few hundred milliseconds of transform and evaluation, seconds on a loaded machine, and the first test of a file used to pay it inside its own timeout (this was the cause of "starts on the community settings" timing out its 1 s wait twice). A file that opens a view awaits `preloadSurface()` once at its top. `lazy-presentation.test.ts` is the one file that must not: it proves nothing of this loads before a view opens.
- **fast-check runs with random seeds**, on purpose: each run explores new inputs. A failure prints its seed and path (`Property failed after 13 tests { seed: -729116352, path: "12:1:0:…" }`, then the shrunk counterexample), and with `CI=1` the same text lands in `reports/junit.xml`. Every property here calls fast-check's own `assert`, which does not swallow it; keep it that way, and never catch around an `assert(property(…))`. To replay a failure, pass both values as the second argument to that `assert`, `assert(property(…), { seed: -729116352, path: "12:1:0:…" })`: it runs only the failing case. Fix the cause, then remove the two options, and keep the counterexample as an `examples` entry or a plain test if it is worth keeping.

## Gate and pre-push hook

`npm run verify` (`scripts/verify.mjs`) is the one gate. It has two kinds of stage:

1. `format:check`, `lint` and `typecheck` start together. They read the sources and write nothing, so they do not disturb each other.
2. `test:coverage`, `analyze`, `build`, `check:dist` and `check:notices`, each alone and in this order. `check:dist` and `check:notices` read the fresh `dist/`, so they stay behind `build`.

`npm run verify:full` adds `test:mutation` as a last stage.

- **Output.** Each step of the group writes into a buffer and its output is printed whole when the step ends, between `--- name ---` and `--- name: ok, 12.3 s ---` (or `FAIL (exit 1)`), so lines of two steps never mix. The step that ends first is printed first; a failed step is printed like the others. A step that runs alone keeps the terminal, with live lines and colours; the group's output gets colours too when the terminal has them.
- **Stop.** When a step of the group fails, the other two still finish and show their results, and then the gate stops: no later step starts. A later step that fails stops the gate at once.
- **Summary and exit code.** The last lines name every step with `ok`, `FAIL` or `not run` and its duration, then the wall-clock total. The exit code is that of the first failed step in gate order (format, lint, type check, then the rest), or 0. `tests/unit/scripts/verify.test.ts` proves this on a fake runner whose steps end when the test says so: what starts together, what waits for the slowest, the buffering, the stop, the exit code; two tests start real `node` processes for the buffering.
- **Time.** Measured on 2026-11-22 in a four-core container shared with other agent sessions, so never on an idle machine. *Before* (one step after the other), three runs at a load average of 1.6 to 4: 114.6, 101.4 and 112.4 s (the PBI-64 review measured 81 to 87 s on an idle machine). The steps took `format:check` 5.0 to 6.6 s, `lint` 30.5 to 34.9 s, `typecheck` 15.6 to 17.2 s, `test:coverage` 45.7 to 53.0 s, the other four together about 5 s. Started together, the group takes as long as its slowest member, `lint`, so the same three runs would have taken 90.8, 80.7 and 90.4 s (the summed durations minus the two shorter steps: a floor, because the three compete for cores). *After*, measured: the old and the new script alternating at a load average of 16 to 20: old 319, 347 and 322 s, new 249 and 194 s (a third new run was killed by the machine running out of memory; the gate reported `lint` FAIL with exit 137 and stopped, as designed). That ratio shows the direction, not the size. Memory: the group's peak was 2.9 GB, lint alone 3.0 GB, `typecheck` 1.0 GB, `test:coverage` 1.2 GB, so the group needs no more than `lint` did. An idle-machine run of the new script is not measured yet.
- **No ESLint `--cache`.** `eslint --cache` was tried and left out, because it can pass a stale result. ESLint's cache keys on a file's own content and the config, but a type-aware finding can depend on another file. Proof, 2026-11-22, with two planted files: `a.ts` has a `switch` over `Kind` from `b.ts` that lists every member; with `Kind = "a" | "b"` the cache fills and `a.ts` is clean. Then only `b.ts` gains `"c"`: `eslint --cache` still exits 0 for both files (with `--cache-strategy metadata` and with `content`), and the same run without the cache exits 1 with `switch-exhaustiveness-check: Cases not matched: "c"`. That is the rule this repository turned on for exactly this reason (see Lint below), so a cached local lint would hide the break the gate exists to find. If the cost of lint matters again, the way is fewer type-aware rules or a smaller TypeScript project, not a cache.
- **Pre-push hook.** `.githooks/pre-push` is a launcher of two lines in `sh` (git runs hooks through it, also on Windows); `scripts/pre-push.mjs` decides and runs the gate through the same `runGate` as `npm run verify`. A push whose changed files are all documents (a path under `docs/`, or a file ending in `.md`) runs only `format:check`; anything else runs the whole gate. A push of one other file runs the whole gate, and so does a push whose range cannot be worked out.
  - **What is compared.** git hands the hook `<local ref> <local sha> <remote ref> <remote sha>` per ref on stdin. For a ref the remote has, the files are those that differ between the remote's commit and the pushed one (`git diff --name-only --no-renames`, so a file moved into `docs/` counts with both its paths). For a new branch (remote sha all zeros) the base is the merge-base with the remote's default branch (`refs/remotes/<remote>/HEAD`, else `main`, else `master`). A deleted ref (local sha all zeros) pushes nothing and adds no file; a push that only deletes runs `format:check`.
  - **Tags.** A tag is compared like a branch, so it is "documents only" only when the commits it adds to the default branch change documents only. A tag on a commit the default branch already has adds no file, so a release tag pushed from `main` runs `format:check` only; the release workflow runs the whole gate anyway.
  - **In doubt, the whole gate.** No lines on stdin or one that is not four fields with two object ids, no default branch to compare a new ref with, an object the clone does not have (a force push over a commit that was never fetched), a tag on something that is not a commit.
  - **Why documents are safe to skip.** No step of the gate reads a Markdown file or `docs/`: `.prettierignore` leaves out `docs/` and `*.md`, oxlint, ESLint and fallow ignore `docs/**`, the TypeScript projects include no document, no test or script opens one (`grep -rn "docs/" tests scripts --include=*.ts --include=*.mjs` finds one comment), and `check:notices` reads the lockfile and `dist/`. So for a document `format:check` is close to a no-op today; PBI-64 keeps it as the one step a documents-only push runs (about 5 s), and it would catch a document the day `.prettierignore` stops ignoring them. What documents can still break is outside the gate: `tests/e2e/vaults/basic/**/*.md` (the e2e vault) and `skills/**/*.md` (the `skills` CI job), which a `*.md` rule also covers. Change either and run `npm run test:e2e` or the skills tests yourself.
  - `tests/unit/scripts/pre-push.test.ts` covers the path rule, the parsing, each decision above on a fake git, and `realGit` on a real repository in a temporary folder (new branch, a move into `docs/`, an annotated tag, an object that is missing, a remote without a default branch).
  - `git push --no-verify` still skips the hook, and `npm ci` installs it (`prepare`).

## Lint

`npm run lint` runs oxlint, then ESLint. oxlint owns the rules that need no type information (`.oxlintrc.json`); ESLint owns the ones that do and the plugin rules (`eslint.config.mjs`, whose oxlint block turns off what oxlint covers). Three rules are on because nothing else catches them:

- `eqeqeq` and `typescript/no-non-null-assertion` in oxlint: `==` and `!=`, and `value!`. Narrow with a check or throw a clear error instead of asserting.
- `@typescript-eslint/switch-exhaustiveness-check` in ESLint (it needs types): a `switch` over a union lists every member, so a new member breaks the build where it is not handled. A `switch` with a `default` over a union does not pass; write the cases out, or use conditions when only a few members matter (`pathsToRead` in `index-batches.ts`).

Each was proven with a planted violation before it was turned on (no finding) and after (the finding, in the tool named above). A rule that cannot be shown to fail on a plant does not belong in the config.

## Mutation testing

- `npm run test:mutation` runs incrementally; `npm run test:mutation:full` re-runs every mutant.
- Stryker mutates `src/domain` and `src/application` and runs only their unit tests, with the TypeScript checker on.
- Before pushing a change to one module, run Stryker on its files only: `npx stryker run configs/stryker.config.mjs --mutate "src/domain/communities/**/*.ts,src/application/communities/**/*.ts"`. The communities module scores 100 %; keep it there.
- Thresholds: break 75, low 80, high 90. Never lower them.
- A `// Stryker disable` comment needs its reason on the same line.
- Reports land in `reports/mutation/`. The nightly GitHub workflow runs `npm run test:mutation` against the cached `reports/stryker-incremental.json`, so only mutants whose code or tests changed run again; started by hand with `full` it re-runs every mutant. A failed night opens or updates the issue "Nightly mutation run failed".
- **An incremental run does not re-test a survivor against a new test.** After adding tests to kill a survivor, run with `--force` (`full` in the workflow); the edge run's survivors for `SHELL_VIEW_TYPE` and the nav icon stayed "Survived" in an incremental run although a hand-planted copy of each failed the new tests.
- A timed-out mutant counts as killed. On a loaded machine a slow test turns survivors into timeouts, so read the "timed out" count beside the score.

### The edge layers

`npm run test:mutation:edge` (`configs/stryker.edge.config.mjs`, with `configs/vitest.stryker.edge.config.ts` for the unit and dom projects) mutates what the gated run skips: `src/infrastructure/obsidian/**`, `src/infrastructure/memory/**`, `src/presentation/**/*.ts` (not the `.vue` files) and `src/bootstrap.ts`.

- **Informational.** No `break` threshold, and not part of `verify`, `verify:full` or the pre-push hook: the score is read, never enforced. Its cache is `reports/stryker-edge-incremental.json`, its report `reports/mutation-edge/`. Both configs use the `.stryker-tmp` folder, so do not run them in one checkout at the same time.
- **Cost.** 40 files and about 990 mutants; a full run took 25 to 41 minutes on four cores (two test runners, two checkers; the longer one with another suite running), because the dom tests are slower than the unit tests of the inner layers. One file: `npx stryker run configs/stryker.edge.config.mjs --mutate "src/infrastructure/obsidian/shell/settings-mirror.ts"` (`--force` ignores the cache).
- **A survivor is a lead, not a verdict.** Plant the mutation by hand (edit the line, run `npx vitest run`) before writing a test: an incremental run can report a survivor that a test already kills, and some survivors are equivalent (the result is the same, only the cost differs). Write a test only where nothing fails, and state behaviour in it: "a closed surface unmounts its Vue app and removes its scope class", not "calls `releases.push`".
- **Score.** 94.81 % (506 killed, 6 timed out, 26 survived, 2 without coverage) after the tests of 2026-11-22; 85.37 % before them on the same code (the reviewer's earlier run: 82.75 %). ## Browser harness

`npm run dev:ui` serves `harness/`: two surfaces on one runtime (one of them 320 px wide, so its frame shows the navigation as a row), each with its own in-memory route, a theme switch, and visible notices. `?scenario=` selects the state:

The fake host (`harness/fake-host.css`) plays Obsidian 1.15.1's default theme: the theme variables read from the running app in light and dark, and Obsidian's base rules that reach plugin markup (button chrome, text inputs, heading sizes and margins). ## End-to-end tests in Obsidian

`npm run test:e2e` builds the plugin and runs `tests/e2e/specs/*.e2e.ts` with WebdriverIO and [`wdio-obsidian-service`](https://github.com/jesse-r-s-hines/wdio-obsidian-service) in a **real Obsidian app**. Background and alternatives: [Testing research](../design/research/Testing%20research%20-%20Obsidian%20end-to-end%20tests.md).

- **Versions.** The suite runs the latest Obsidian app on the latest installer (`latest/latest`); CI does the same.
  - `OBSIDIAN_VERSIONS` takes other app/installer pairs. For example, `earliest/earliest` is `minAppVersion` (1.15.1) on the oldest installer it accepts (1.5.8, Electron 28).
  - In PowerShell, set it with `$env:OBSIDIAN_VERSIONS="earliest/earliest"` first.
- **First run.** The first run downloads Obsidian into `.obsidian-cache/` (git-ignored, about 1.3 GB unpacked). Never commit or share it: Obsidian's terms forbid redistribution.
- **Display.** On Linux without a display, run `xvfb-run -a npm run test:e2e`. Windows and macOS need nothing extra.
- **Isolation.** Each spec file gets a fresh Obsidian with a copy of `tests/e2e/vaults/basic`, and `dist/` is installed as the plugin. `vault-ready.e2e.ts` switches to a fresh copy of the reference vault with `browser.reloadObsidian({ vault })`, which Obsidian has never indexed.
- **Reference vault.** `scripts/reference-vault.mjs` writes the desktop reference profile of F-21: two communities, 200 Punkte and 2,000 notes with frontmatter in total, plus 200 plain Markdown notes without it. `referenceVault({ seed, points, records, plain })` returns paths and texts; `writeReferenceVault(target, options)` replaces the folder with them. The same seed gives the same bytes: a seeded generator, no clock, no `Math.random` (`tests/unit/scripts/reference-vault.test.ts`). Records follow ADR 0007 (`schema: weg-manager.<type>/v1`, `id: <type>-<uuid>`, snake_case keys, `community_id` on everything but communities). Only `community` is specified so far, so the rest is the generic type `item` (`kind: point` or `note`); the generator follows the real types as they are built. The profile's 1,000 attachments are left out: the index reads frontmatter, never a binary. `npm run vault:reference` (part of `test:e2e`) writes it into the git-ignored `tests/e2e/vaults/reference/`; it is never committed.
- **Probe plugin.** `tests/e2e/probe-plugin/` is a second plugin for the suite only. `npm run build:probe` (part of `test:e2e`) bundles it with `configs/vite.probe.config.ts` from the real adapter source into `tests/e2e/probe-plugin/dist/` (git-ignored), and `wdio.conf.mts` installs it beside `dist/`. It exposes the Obsidian `NoteStore` as `plugins.noteStoreProbe.api`, so a spec calls the store without any hook in the plugin itself. `plugins.noteStoreProbe.events` is the note index for the reference types (`counts()`, `titleShown(path, title)`), built on the probe's own runtime before the plugin's real `hostEventsLayer`, as the plugin composes them; the recorder marks `index:ready` when its first build is published. `plugins.noteStoreProbe.startup` records from the probe's `onload` on how Obsidian got ready (layout, `create`, `changed`, `resolve`, `resolved`, with cache counts at the layout and the first `resolved`), and runs the plugin's real `hostEventsLayer` on a runtime of its own, with a count of cached notes at its `LayoutReady` and `VaultReady`.
- **Cache.** The download cache is `.obsidian-cache/` in the checkout. In a git worktree, a symlink to the main checkout's cache avoids a second download.
- **Language.** Without a stored choice Obsidian takes its language from Chromium's locale, which is `en-US` in CI and containers. `wdio.conf.mts` passes `--lang=de`, so Obsidian and the plugin start German and the specs assert German texts. `language.e2e.ts` switches to English the way Obsidian's own setting does: `localStorage` key `language`, then a plugin reload.
- **Writing specs.** `browser.executeObsidian(({ app, obsidian }, ...args) => …)` runs code inside Obsidian. The function is serialised, so pass values as arguments; closures do not work. Shared helpers live in `tests/e2e/support.ts`: console spy, open view, `data.json`, plugin reload, settings tab content, light/dark switch.
- **Waiting in specs.** No spec waits a fixed time for an effect. After a write (a note saved, created, deleted or edited from outside) the app follows about 100 ms later (the index batches for `INDEX_BATCH_QUIET`), and a lazily loaded part (the badge beside "Datenprobleme", a section's screen) comes after its own snapshot. So a click or a read that depends on the write waits for what shows it first:
  - `expectListed(names)` for the list, `expectSummary(name, text)` for a card's kind and unit label (the form opens on what the view knows, so a form opened early starts from the old values and misses a conflict), `expectNotice(text)`, `eventually(read, expected, what)` for any read (it shows the last value on a timeout), the auto-waiting `expect(…)` matchers for elements, `browser.waitUntil` for the rest.
  - **A negative check never passes empty.** "Nothing was written", "no notice", "VaultReady only once" first wait for a positive sign that comes after: a later write whose effect the view shows (`communities-newer-schema.e2e.ts`, `events.e2e.ts`), a second file from outside that the settings tab follows (`external-settings.e2e.ts`, `settings-and-theme.e2e.ts`), a `resolved` that an edit makes Obsidian fire (`vault-ready.e2e.ts`). Then the check reads.
  - **A spec that records events** starts with `cacheIdle()` (`tests/e2e/support.ts`): a freshly started Obsidian is still indexing the vault's own notes, and its `changed` events would land inside the first scenario (`note-store.e2e.ts` failed once on a loaded machine with three late `changed`). A note is edited, and once its `changed` and the `resolved` after it have come, the cache has worked through everything before it.
  - **Colours** are read at rest: `settleColours()` (`tests/e2e/appearance.ts`, called inside every measuring helper and after the pointer is parked) forces a style recalculation and jumps every running transition and finite animation to its end, repeating until none is left. It waits for neither frames nor time, because a window without frames (CI without a window manager) never advances a fade: the dialog's texts were once read with their light-theme ratios in the dark theme, behind a fixed `pause(400)`.
  - **One pause stays**, in `no-network.e2e.ts`: "no request left" has no signal when it holds, and a request that left shows as a resource entry only after its network round trip, so it lets one second pass (the reason is in the spec). `grep -rn "pause(\|setTimeout(" tests/e2e` finds it and nothing else; the fidelity scenarios in `tests/support/notes/scenarios.ts` and `readiness-scenario.ts` still take a settle time as an argument (`SETTLE_MS`, 400), which the test double step replaces.
- **Texts.** Specs read user-visible texts from the typed German catalog (`import { de } from "../texts"`, a re-export of `src/application/messages.ts`: plain data of the application layer, loadable in Node), so a wording change touches the catalog. Literal sentences stay in `language.e2e.ts` only.
- **Gate.** `test:e2e` is not part of `verify`, because it needs a display and a download. CI runs it as a separate `e2e` job, which is not a required check yet (see [github-setup.md](github-setup.md)). The release workflow runs it too, in its read-only `build` job, and a failing e2e run stops the release. A change to lifecycle, settings tab, theme, pop-out, view state or vault behaviour needs a passing e2e run.

## Scanner-equivalent lint

`npm run lint:scanner` approximates the source scan of Obsidian's community directory. It runs `configs/eslint.scanner.config.mjs` over the repo: only `eslint-plugin-obsidianmd`'s `recommended` config, the rule changes and the fixed ignore list from the plugin's [scanner configuration](https://github.com/obsidianmd/eslint-plugin/blob/a998a5992b7bf9b6f3e0fe1e61a3ad180546f4a5/docs/configuration.md#community-plugin-scanner-configuration). Our own ignores (such as `.claude/**`) and Vue rules do not apply.

- **What it adds to the scanner's list.** Files git does not track are skipped, because the scanner sees a clone. Bundled JavaScript outside `src/` is skipped by the scanner's content rule. `.js` files are linted without type information, because no tsconfig here takes them in.
- **Not exact.** The scanner also turns most remaining errors into warnings and adds stricter layers for new submissions. Read the output as a preview, not a verdict.
- **Informational.** It is not part of `verify`. CI runs it as the last step of the `verify` job with `continue-on-error`, so findings show in the log and as a warning annotation but never block.
- **Known failure.** `.claude/skills/archify/explainer/reader.js` fails with `no-unsanitized/property` (it assigns `innerHTML`) and other errors. The owner decided to deal with it at submission time; options are in [Plugin research](../design/research/Plugin%20research%20-%20Obsidian%20best%20practices.md) item 1.
